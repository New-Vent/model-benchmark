# 로컬 LLM → AWS Bedrock 전환 근거

7개 버전(v1~v7)에 걸친 로컬 LLM(Ollama) 벤치마크에서 실제로 관측된 데이터를 근거로,
이벤트 페이지 생성/수정 파이프라인의 모델 실행 방식을 로컬 자체 호스팅에서
AWS Bedrock(상업 API)으로 옮기는 이유를 정리한다. 감이 아니라 `versions/v1~v7`의
결과 CSV·README에 실제로 남아있는 숫자만 근거로 쓴다.

## 요약

로컬 7~8B급 모델로 "쓸 만한 조합"을 찾는 데 7번의 버전 개편과 수십 개 군의
재설계가 필요했고, 그 과정에서 드러난 문제는 **모델을 더 잘 고르면 풀리는 문제가
아니라 로컬 소형 모델 자체의 구조적 한계**였다. 반면 그 한계를 우회하기 위해 들인
엔지니어링 비용(패치 방식 재설계, 오퍼레이션 명 우회, 기기별 캘리브레이션)은
버전이 늘수록 줄지 않고 계속 늘었다. Bedrock 전환은 "로컬이 느려서"가 아니라
"로컬 소형 모델의 실패 모드를 팀 코드로 계속 땜질하는 비용이, 관리형 API를 쓰는
비용을 넘어섰다"는 판단이다.

## 1. 로컬 모델은 버전마다 다른 방식으로 무너졌다

| 버전 | 발견 | 성격 |
| --- | --- | --- |
| v1 | exaone 무단 변경(요청하지 않은 필드까지 수정) 20%, gemma3:4b 환각 8.3%, qwen3:8b 출력 잘림 14%로 이후 버전에서 완전 제외 | 모델별 실패 모드가 전부 다름 — 공통 해법 없음 |
| v2 | gemma3:4b, K군(구조 변경 패치)에서 **150건 중 0건 성공** | 패치 계열 자체를 못 푸는 모델이 존재 |
| v4 | 인공 문서가 아니라 **실제 제품 템플릿**으로 채점 기준을 바꾸자 v1~v3의 결론이 뒤집힘 — JSON 패치(J/K)보다 HTML 직접 편집(S)이 우세로 역전 | 인공 벤치마크 결과가 실제 마크업에서 재현되지 않음 |
| v5 | qwen 계열은 100% 동률인데, exaone은 JSON 생성(J-T)에서만 **1/50로 붕괴**(텍스트 필드에 태그 주입) | 같은 모델도 출력 형식만 바꾸면 붕괴 |
| v6 | "삭제"라는 오퍼레이션 **이름 자체**가 회피를 유발했고, 같은 동작을 `itemCount`로 표현만 바꾸자 성공률이 복구됨 | 실패가 능력이 아니라 프롬프트 표현에 좌우됨 — 재현성이 낮음 |

다섯 개 버전에서 다섯 가지 다른 실패 모드가 나왔다는 것은, 특정 모델 하나를
회피하면 끝나는 문제가 아니라 **로컬에서 돌릴 수 있는 크기(7~8B)의 모델 전반이
프롬프트·출력 형식·오퍼레이션 명명 방식에 민감하게 반응**한다는 뜻이다. 이런
민감도는 모델을 교체해도 재발한다 — v1에서 걸러진 문제가 v4에서 다른 모습으로,
v6에서 또 다른 모습으로 다시 나타났다.

## 2. "안전한 조합"을 찾는 비용이 버전마다 커졌다

- v1: 모델 선정 (7개 군, 4대, 3362행)
- v4: 채점 기준 자체를 실제 템플릿 기반으로 다시 설계(`checks_v4.py` 신설)해야
  했고, 그 결과 이전 결론(J/K 우세)이 뒤집혔다.
- v6: 실패를 피하려고 **오퍼레이션 스키마 자체를 다시 설계**(`patch_ops_v6.py`,
  삭제 → `itemCount` 변경)해야 했다.
- v6는 확장 케이스(STRUCT6~9, K-STRUCT-V)가 아직 미실행, v7(CHAIN7 실전 체인
  검증)은 파일럿 1건만 진행된 상태로, "안전권"이 아직 확정되지 않았다.

즉 로컬 모델을 프로덕션에 쓸 수 있는 수준으로 끌어올리는 작업은 모델 선택에서
끝나지 않고, **채점기 재설계 → 스키마 재설계 → 프롬프트 표현 재설계**로 계속
번져 나갔다. 이 비용은 앞으로도 새 케이스(체인 길이 증가, 새 컴포넌트 추가)마다
반복될 가능성이 높다 — v6에서 이미 한 번 반복됐다.

## 3. 로컬 운영 자체의 구조적 비용

- **기기 편차**: `base/engine.py`가 캘리브레이션과 회차별 생성 속도(발열로
  느려지는지)를 따로 측정해야 할 만큼, 같은 모델·같은 버전이라도 실행 기기에
  따라 결과가 달라진다. `env_v*_*.json`에 digest·기기 정보를 남기는 것도 이
  편차를 추적하기 위함이다.
- **버전 드리프트 확인 비용**: README의 "사전 준비"에 `ollama list`로 digest가
  일치하는지 사람이 직접 확인하라는 절차가 있다 — 모델 파일 자체가 팀원마다
  다를 수 있다는 뜻이다.
- **인력 확장 비용**: 실행마다 팀원(도하·윤기·주호·지원) 각자의 로컬 GPU/Ollama
  환경이 필요하고, 결과를 모으고 나서야 비교가 가능하다. 팀·모델·케이스가
  늘어날수록 이 조합 비용이 곱으로 늘어난다.
- **미완성 도구 부채**: 버전 간 정합 비교(McNemar)를 위한 `tools/compare_v1_v2.py`가
  문서(README, `docs/methodology.md`)에는 계속 언급되지만 7개 버전이 지나도록
  실제로 구현된 적이 없다 — 로컬 실험을 관리하는 인프라 자체가 계속 뒤로 밀렸다.

## 4. Bedrock으로 옮기면 없어지는 변수들

| 로컬(Ollama)에서 겪은 문제 | Bedrock에서의 해소 방식 |
| --- | --- |
| 기기별 digest·성능 편차, 발열로 인한 속도 저하 | 모델 실행이 관리형 인프라로 이동 — 팀원 로컬 하드웨어가 결과에 영향을 주지 않음 |
| 팀원마다 모델 버전(digest)이 어긋날 위험 | Bedrock의 모델 버전 고정(model ID)으로 전원이 항상 동일 가중치 호출 |
| 7~8B급으로 제한된 모델 크기 → 프롬프트 표현 민감도(v6) | 더 큰 파라미터의 파운데이션 모델에 접근 가능 — 이번 벤치마크에서 반복 관측된 "이름만 바꿔도 실패" 현상은 대체로 소형 모델일수록 심함 |
| GPU 보유 여부에 따라 실행 가능 인원이 제한 | API 호출만으로 전원이 동일한 조건에서 실행 |
| 모델 교체 시마다 자체 인프라(pull, 캘리브레이션) 재구축 | 모델 교체가 API 파라미터 변경 수준으로 축소 |

## 5. 인지하는 트레이드오프

설득력을 위해 반대 근거도 남긴다 — 다음은 이번 전환으로 새로 생기는 비용이며,
이를 상쇄할 만큼 위 문제들이 크다고 판단했다.

- **호출 비용 발생**: 로컬은 전기·하드웨어 비용 외 한계비용이 0에 가까웠지만,
  Bedrock은 호출량에 비례한 과금이 발생한다. 다만 v1~v6에서 반복된 재설계
  비용(사람의 엔지니어링 시간)이 이미 API 비용보다 크다고 본다.
  실제 트래픽 기준 예상 호출량과 단가는 별도로 산정이 필요하다.
- **외부 의존성**: 네트워크 장애·리전 장애 시 생성 파이프라인이 함께 멈춘다.
  로컬은 오프라인에서도 동작했다.
- **데이터 전송**: 이벤트 콘텐츠(사용자 입력 포함 가능)가 외부로 나간다 — 민감
  정보 포함 여부에 따라 별도 검토가 필요하다.
- **벤치마크 자산의 재사용 범위**: `base/registry.py`·`base/checks.py`·
  `base/component_library.py`(채점·컴포넌트 정의)는 모델 비의존적이라 그대로
  재사용 가능하지만, `base/run.py`의 Ollama 호출부는 Bedrock 클라이언트로
  교체해야 한다.

## 6. 완전 생성/수정 케이스만 놓고 본 토큰 대비 완성도

v6 J-STRUCT·K-COUNT는 성공률 자체는 최고 수준까지 끌어올렸다(K-COUNT
qwen2.5-coder:7b 100%, 320토큰). 하지만 **LLM이 구조만 결정하고 나머지 응답
폼은 사용자가 채우는 방식**이라 완전 자동 생성을 목표로 하는 프로젝트 요구와
맞지 않아 후보에서 제외한다. 이후 비교는 **LLM이 응답을 끝까지 완성하는
케이스**(v4 S-E·K-T, v5 S-T·J-T)만 대상으로 하고, Bedrock에서는 토큰이 곧
과금 단위이므로 지표를 다음과 같이 정의한다.

```
완성도(%) = all_ok 성공률           # 하드+소프트 실패 0건, 완전 통과
토큰(P+E) = prompt_tokens + eval_count 평균
효율      = 완성도(%) / (토큰(P+E) / 1000)     # 1,000토큰당 완성 건수
```

| 순위 | 케이스 | 모델 | n | 완성도(%) | 토큰(P+E) | 효율(완성/1k tok) |
| ---: | --- | --- | ---: | ---: | ---: | ---: |
| 1 | J-T (JSON 신규생성, v5) | qwen2.5-coder:7b | 50 | **100.0** | 542 | **1.85** |
| 2 | J-T | qwen2.5:7b | 50 | **100.0** | 550 | 1.82 |
| 3 | S-T (HTML 신규생성, v5) | qwen2.5-coder:7b | 50 | 100.0 | 750 | 1.33 |
| 4 | S-E (HTML 수정, v4) | qwen2.5-coder:7b | 25 | 80.0 | 1217 | 0.66 |
| 4 | S-E (HTML 수정, v4) | qwen2.5:7b | 25 | 80.0 | 1220 | 0.66 |
| 6 | S-T | qwen2.5:7b | 50 | 2.0 | 753 | 0.03 |
| 7 | K-T (JSON 패치수정, v4) | qwen2.5-coder:7b | 51 | 5.9 | 918 | 0.06 |
| 8 | K-T | qwen2.5:7b | 49 | 0.0 | 919 | 0.00 |

참고(제외 대상 — 구조만 생성, 순위 밖):

| 케이스 | 모델 | n | 완성도(%) | 토큰(P+E) | 효율 |
| --- | --- | ---: | ---: | ---: | ---: |
| K-COUNT | qwen2.5-coder:7b | 20 | 100.0 | 320 | 3.12 |
| J-STRUCT | qwen2.5-coder:7b | 85 | 82.4 | 608 | 1.35 |
| J-STRUCT | qwen2.5:7b | 128 | 54.7 | 572 | 0.96 |
| K-COUNT | qwen2.5:7b | 55 | 36.4 | 366 | 0.99 |

**읽는 법**

- **신규 생성**: J-T가 두 후보 모델 모두에서 완성도 100%, 토큰은 542~550으로
  가장 적다 — 순위 1·2위, 효율 1.82~1.85로 압도. S-T는 qwen2.5-coder:7b에선
  100%지만 qwen2.5:7b에선 **2.0%로 붕괴**(모델 의존적, 재현성 낮음).
- **기존 문서 수정**: 완성도 100%짜리 방식이 아직 없다. S-E가 두 모델 모두
  80.0%로 유일하게 일관되지만, 토큰은 J-T의 약 2.2배(1217~1220 vs 542~550).
  K-T(패치 수정)는 토큰이 적어도(918~919) 완성도가 0~5.9%라 효율 계산 자체가
  무의미 — v4에서 확인된 "패치 방식은 실제 마크업 수정에 못 쓴다"는 결론과 일치.
- **결정**: 신규 생성은 **J-T(JSON 완전 생성) 채택** — 완성도·토큰·모델 간
  일관성 세 축 모두 1위. 수정 경로는 완성도 100%가 없으므로 S-E를 임시 채택하되,
  다음 버전에서 토큰 절감 또는 완성도 개선 여지를 별도로 검증해야 한다.

## 7. 체인(파이프라인) 전체로 보면 로컬 LLM은 훨씬 더 나쁘다

**함정**: 단계별 성공률을 그냥 더하면 실제보다 좋아 보인다. v3 README가 직접
잡아낸 사례 — qwen2.5:7b는 "모델 x 군" 표에서 CHAIN2 합산 75/90(83%)이지만,
생성→패치→JS추가→값수정 **4단계가 끝까지 이어진 비율은 0/5(0%)**(주호,
1기기). 3단계(JS추가)에서 매번 걸려 이후 단계가 `chain_blocked_by_previous_
stage_failure`로 전부 막혔다.

### 종단(end-to-end) 완주율 — 전체 결과 CSV 재집계 (`pair`+`prompt_id`+`seed`+`runner` 단위로 전 단계 hard_ok 재확인)

| 버전 | 체인 | 단계 구성 | qwen2.5:7b | qwen2.5-coder:7b |
| --- | --- | --- | ---: | ---: |
| v2 | CHAIN1 | 2단계: J생성→K패치 | 10/10 (100%) | 5/5 (100%) |
| v3 | CHAIN2 | 4단계, 순수 JSON 노선 | 1/15 (6.7%) | 0/15 (0%) |
| v3 | CHAIN3 | 4단계, 순수 HTML 노선 | 6/15 (40.0%) | 5/15 (33.3%) |
| v3 | CHAIN4 | K 실패 시 E로 우회 | 12/15 (80.0%) | 1/15 (6.7%) |
| v3 | CHAIN5 | JSON 생성·수정 + HTML로 JS추가 | 9/15 (60.0%) | 8/15 (53.3%) |
| v3 | CHAIN6 | HTML 생성·수정 + JSON으로 JS추가(혼합 우회 설계) | **15/15 (100%)** | **15/15 (100%)** |
| v7 | CHAIN7J/7S | 확정 조합 재검증(파일럿, n=10) | 10/10 · 9/10 | 10/10 · 10/10 |

**읽는 법**

- 체인이 **2단계**(v2)면 100% — 문제가 안 보인다. **4단계**(v3)로 늘리자마자
  같은 두 모델이 **0~40%**로 추락한다.
- **포맷을 한 가지로만 통일한 체인(CHAIN2 JSON전용, CHAIN3 HTML전용)이 가장
  나쁘다** — 개별 단계 성공률은 80~100%인데 4단계를 곱하면 0~40%로 무너진다.
  단일 케이스 벤치마크(§6 표)만으로는 이 손실이 안 보인다.
- **회복 수단은 "더 좋은 모델"이 아니라 "체인 라우팅 재설계"였다** — CHAIN6은
  같은 모델로, 생성·수정은 HTML/JS추가만 JSON으로 섞은 우회 설계 이후에야
  0%→100%로 회복됐다. 모델 선택만으로는 안 풀리고, 체인마다 별도의
  엔지니어링(라우팅 재설계+검증)이 필요했다.
- **v7(확정 조합)도 아직 파일럿(2기기·n=10)뿐** — 90~100%로 보이지만 v1급
  표본(4기기·3000행 이상)으로 검증된 적은 없다.

### 함의

서비스가 실제로 필요한 건 개별 케이스 통과가 아니라 **생성→수정→JS추가→값수정
전체가 한 번에 이어지는 것**이다. 로컬 최상위 모델(qwen 계열)도 개별 단계로는
80~100%지만, 체인으로 이으면 라우팅을 잘못 짜면 0%까지, 잘 짜도 파일럿
검증뿐인 90~100%까지가 현재 위치다. 단계당 성공률이 95%→99%로만 올라가도
4단계 곱셈 효과는 0.95⁴=81% vs 0.99⁴=96%로 커지므로, Bedrock 전환의 이득은
단일 케이스 성공률 몇 %p가 아니라 **체인 종단 성공률에 지수적으로 반영**된다 —
지금 CHAIN2→CHAIN6처럼 라우팅을 새로 설계해 겨우 버티는 구조를, 모델 자체의
안정성으로 대체하는 것이 이번 전환의 실질 목표다.

## 8. 값 수정은 되는데 컴포넌트 추가/삭제는 로컬 LLM의 한계로 남는다

### 8-1. 값 수정 vs 구조 변경 (v4 README §3 원표 기준, hard_ok)

| 작업 | 포맷 | qwen2.5:7b | qwen2.5-coder:7b | exaone3.5:7.8b |
| --- | --- | ---: | ---: | ---: |
| 문구 교체(값 수정, KT1·KT2) | K-T(JSON 패치) | 20/20 (100%) | 20/20 (100%) | 20/20 (100%) |
| 구조 변경(항목 추가·삭제, KT3·KT4) | K-T(JSON 패치) | 7/20 (35%) | 4/20 (20%) | 3/20 (15%) |
| └ 삭제 단독(KT3, "혜택 하나 빼줘") | K-T | **0/5** | **0/5** | **0/5** |
| 문구 교체+구조변경 전체(SE1~5) | S-E(HTML 직접편집) | 25/25 (100%) | 25/25 (100%) | 20/25 (80%) |

- JSON 패치(K)는 "값만 바꿔라"는 100%지만 "추가/삭제해라"로 바뀌는 순간
  20~35%로 떨어지고, 삭제만 따로 떼면(KT3) **4개 모델 전부 0/5** —
  지배적 실패는 `no_ops`(패치 오퍼레이션 자체를 안 냄).
- 이 패턴은 v2 K군(블록 추가 K3 0~3/10, 블록 삭제 K9 0/10·0/5)에서 이미
  나타났고, v4에서 실제 제품 템플릿으로도 그대로 재현됐다 — 우연이 아니라
  반복되는 구조적 한계.
- **HTML 직접편집(S)으로 바꾸면 추가·삭제 포함 25/25(100%)로 회복** — "구조
  변경 자체를 로컬 LLM이 못 한다"가 아니라 **"JSON 패치로 구조 변경을
  지시하면 그 오퍼레이션을 아예 안 낸다"**가 정확한 진단이다.

### 8-2. 지금 성공률은 이미 로컬 LLM 예산에 맞춰 축소한 과제 위에서 나왔다

| 항목 | 실제 필요치 | 로컬 캡/설계 | 근거 |
| --- | --- | --- | --- |
| html 출력 | 전체 페이지 생성 1,985~2,443 토큰 | `NUM_PREDICT["html"]=1536` | v4에서 캡 초과로 생성 축을 범위 밖으로 뺌 → v5에서 케이스 단위로만 3072 예외 처리 |
| plan/patch 출력 | — | plan 512 · patch 256 · router 128 | v2에서 J9·K3처럼 내용 많은 케이스의 `truncated` 실패를 100%(17/17)까지 만듦 |
| JS 인터랙션 범위 | — | 카운트다운·아코디언·확인메시지 3종만 | "전역 CSS 전파" 등은 "J만 가능한 기능"이라며 범위 밖으로 명시적 배제(v5 §6) |

지금까지의 성공률(J-T 100%, S-E 80% 등, §6·§7)은 **이미 로컬 7~8B 모델이
감당 가능한 분량으로 줄여놓은 과제** 위에서 나온 숫자다. 실제 서비스가
필요로 하는 분량(전체 페이지 1,985~2,443토큰)은 기본 캡을 이미 초과하고,
인터랙션 종류도 3종으로 제한해 놓은 상태에서조차 구조 변경(추가/삭제)은
패치 방식으로 0~35%까지 떨어진다.

### 8-3. 종합

- **값 수정**(필드 하나 교체)은 포맷·모델 가리지 않고 대부분 해결됨(K-T도 100%).
- **컴포넌트 추가/삭제**는 패치(K) 포맷에서 구조적으로 실패(0~35%, 삭제
  단독 0%)하고, HTML 직접편집(S)으로 우회해야 겨우 회복된다 — 포맷을
  잘못 고르면 드러나지 않던 로컬 모델의 한계다.
- 이마저도 지금 벤치마크가 실제 필요 분량보다 낮은 NUM_PREDICT 캡과
  단순화된 JS 3종으로 축소해서 잰 결과라, 실제 서비스 스펙(더 큰 페이지,
  더 다양한 컴포넌트·인터랙션)으로 넓히면 지금 드러난 한계가 더 커질
  가능성이 높다 — Bedrock 전환으로 더 큰 모델을 쓰면 캡·범위를 줄이지
  않고도 이 구조 변경 실패를 검증할 여지가 생긴다.

## 9. 결론

7번의 버전 개편에서 확인된 것은 "어떤 로컬 모델을 고르느냐"가 아니라
"로컬에서 돌릴 수 있는 모델 크기·운영 방식 자체가 만들어내는 실패 모드가
버전마다 형태를 바꿔가며 재발한다"는 사실이다. 매 버전 채점기·스키마·프롬프트를
다시 설계해 겨우 억누른 실패가 다음 버전에서 다른 모습으로 다시 나타나는
패턴이 v1→v4→v6에서 반복됐고, 이 비용은 케이스가 늘어날수록 줄어들 기미가
없다. Bedrock 전환은 이 반복되는 땜질 비용을, 모델 버전·인프라 편차가 없는
관리형 API로 옮겨 **팀의 엔지니어링 시간을 모델 회피 로직이 아니라 실제
기능(체인·컴포넌트 확장)에 쓰기 위한 결정**이다. 지금까지 쌓은 케이스·채점
기준(`base/registry.py`, `base/checks*.py`)은 Bedrock 모델 비교에도 그대로
재사용해 버전 체계(`versions/v8` 등)를 이어간다.
