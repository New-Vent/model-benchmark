# 모델 비교 축 (Bedrock, v8~v10)

모델은 `model.md` 참고. v1~v7과 달리 **설계는 이미 확정**돼 있고, 여기서 갈리는 건
**어느 모델을 쓰는가**뿐이다 — 최상위 `README.md`의 "v8부터 성격이 다릅니다" 참고.

## 버전별 테스트 방법

| 버전 | 무엇을 쟀나 | 조건 | 규모 |
| --- | --- | --- | --- |
| v8 | **Bedrock 모델 비교** (G 생성 · E 수정 · R 라우터 · C 누적수정) | 백엔드 레지스트리(`Block.shape`) 기준, 정화(sanitize) **뒤**를 채점 | 213행 / 4모델 + 로컬 대조군, 48원 |
| v9 | 슬롯·`class`·`href` 보존 (E1·E2·C1 추가) | v8 + 정화가 **생성/수정 2종**으로 분리(`sanitize_generated`/`sanitize_edited`), 재시도 4회 | 180행 / 4모델, 98원 |
| v10 | **실제 템플릿으로 수정** (D 디자인파괴 · P 보존 · H 준것만) | `template/*.html` 5종 baseline (class 451건, 블록 최대 2,229자) | 4모델, 886원 |

- **v8**: baseline 을 v4~v7 의 `template/*.html` 대신 **백엔드 레지스트리**로 바꾸고,
  정화(sanitize) 뒤를 채점해 "모델 탓"과 "정화 탓"을 분리했다. G·E·R·C 4군 커버리지.
- **v9**: v8 의 정화가 `data-slot`을 양쪽 다 지워버려 슬롯 보존을 아예 못 쟀던 구멍을
  메웠다. 케이스 정의는 v8과 동일, 파이프라인만 다르다. 전체 스위트는 gemma·haiku
  만 확인용으로 재실행(oss120·qwen3-coder 는 v8에서 이미 확정된 값 유지).
- **v10**: v8·v9가 만점만 내서 변별이 안 됐던 게 **baseline이 너무 단순**했기
  때문(class 1개·최대 150자)이라 보고, **실제 디자이너 템플릿 5종**으로 교체. 여기서
  `must` 통과와 실제 디자인 유지가 갈리는 첫 구멍(D축)이 드러났다.

## 1. 라우터 — 갈리는 유일한 축 (v8)

**G·E·C는 네 모델 전부 만점.** 생성·수정·누적수정은 Bedrock 급에서 변별력이 없고,
**라우터만 갈린다.**

| 케이스 | qwen3-coder | qwen2.5:7b(로컬) | gemma-3-27b |
| --- | --- | --- | --- |
| R1 "혜택에 쿠폰 하나 더 넣어줘" | `ADD` ✗ (2/3) | `ADD` ✗ (3/3) | ✓ |
| R5 "버튼 문구 바꿔줘" | `STYLE` ✗ (3/3) | `STYLE` ✗ (1/3) | ✓ |
| R3 "글씨 크고 빨갛게" | `target:null` ✗ (3/3) | ✓ | ✓ |
| R7 "제목·소개 다듬어줘" | ✓ | `benefits` ✗ (3/3) | ✓ |

- 실패는 3회 모두 같은 답이라 우연이 아니다. **라우터는 파이프라인 입구**라 여기서
  틀리면 뒤가 다 무의미하다 — "혜택 하나 더 넣어줘"가 `ADD`로 가면 멀쩡한 블록
  옆에 빈 블록이 생기고, 서버는 정답을 모르니 재시도도 없다.
- **체급이 답이 아니다**: qwen2.5:7b(로컬, 7B) 17/24 vs qwen3-coder-30b(Bedrock,
  30B) 16/24 — 4배 키웠는데 라우팅은 안 올랐다. gemma는 4B(로컬, 패치 전멸)에서
  27B로 가며 만점이 됐다 — **계열마다 강한 축이 다르다.**
- gpt-oss-120b는 라우터 출력이 `{"op":"EDIT","target":"benefits"}`로 짧은데도
  추론 토큰으로 **80토큰/호출**(최대 256)을 태운다 — 한 번은 캡을 다 쓰고 빈
  응답을 냈다. 짧은 출력 작업에 추론 모델은 구조적으로 안 맞는다.

## 2. 생성·수정·누적수정 — 변별력 없음 (v8~v9)

G(생성)·E(수정)·C(누적수정)는 v8·v9 전 구간에서 4모델 전부 만점에 가깝다
(v-summary.md 참고). 출력 품질도 육안 확인 — 한국어 문구 자연스럽고 `href="#"`
보존, 블록 구성 정확, 자리표시자·이모지 없음. **채점이 느슨해서가 아니라 이
급의 모델에서는 실제로 변별이 안 되는 축**이라는 뜻이고, v10이 baseline을 실제
템플릿으로 바꿔서야 비로소 D·H축에서 qwen의 결함이 드러난다.

## 3. 슬롯·`class`·`href` 보존 — v9가 처음 잰 것

v8은 정화(sanitize)가 `data-slot`을 생성·수정 양쪽에서 지워, 모델이 완벽해도
슬롯이 든 케이스는 통과가 불가능했다. v9가 `sanitize_generated`/`sanitize_edited`를
분리하면서 이 축을 처음 측정 가능하게 만들었다.

| 실제 표본 (전부 v9) | 건수 | 결과 |
| --- | ---: | --- |
| E1 — cta 문구 수정 | 18 | **0건** |
| C1-T1 — 누적 체인의 cta 턴 | 18 | **0건** |
| C1 최종 문서 — 3턴 누적 후 | 18 | **class·href·slot 유실 0건** |

- `class`·`href`가 든 baseline은 cta 하나뿐이라 그 표본만 세야 한다 — "E군 전체
  74호출 0건" 같은 집계는 의미가 없다.
- **`slot_invented`(모델이 없던 슬롯을 지어냄) 0건은 "안 난다"가 아니다.** 표본이
  적어(모델당 15호출, baseline 2종) 부재를 증명할 수 없는, 드물지만 치명적인
  실패라고 v9 README가 스스로 경고했다 — **v10에서 실제로 났다**(§5).

## 4. 디자인 파괴 방지 — v10이 처음 잡은 구멍

```
shape   "<ul> 안에 <li> 로 항목을 나열한다"      ← 모델에게 시키는 말
must    "ul li, .benefit-card"                   ← 둘 다 받는다
템플릿   <div class="benefit-card sp-prize-main"> ← 실제 마크업
```

모델이 `shape` 대로 `<ul><li>`로 바꿔버리면 `must` 검사도, 백엔드 `classMap`
검사도 통과하는데 **실제 화면은 CSS가 안 먹어 무너진다.** v10이 이걸 실측으로
처음 잡았다(항목수 `.benefit-card`: 0, `class_lost_benefit-card` 등).

| 모델 | D (must 통과 + 디자인 유지) |
| --- | :-: |
| gemma-3-27b · haiku-4.5 | 9/9 |
| gpt-oss-120b | 3/3 |
| **qwen3-coder-30b** | **1/3** |

qwen은 `data-slot`을 **스스로 지어내고**(`benefit-1-name` 등) 블록을 통째로
다시 썼다 — §3에서 "아직 아무도 모른다"고 남긴 `slot_invented` 위험의 실제
발생 사례. H3(steps)에서도 `.step-card`를 `<li data-slot="step1">`로 감싸며
같은 패턴을 반복했다(`class_lost` 7종 + `slot_invented` 10종).

## 5. 준 것만 쓰기 — 환각 방지 (v10)

v8 E3("혜택 하나 더 추가")에서는 **네 모델 전부** 없는 혜택을 지어냈는데
(항목 수만 세느라 전부 통과했음) — v10은 이 구멍을 "준 것만 쓴다"는 규칙으로
직접 잰다.

| 경계 | 무엇을 보는가 |
| --- | --- |
| H1 | 하나를 줬는데 **둘을 넣으면** 실패 |
| H2 | "더 매력적으로"가 "10GB"→"무려 10GB"면 통과, **혜택 추가**면 실패 — 실무에서 가장 흔한 요청 |

| 모델 | H |
| --- | :-: |
| gemma-3-27b · haiku-4.5 | 9/9 |
| gpt-oss-120b | 3/3 |
| **qwen3-coder-30b** | **2/3** |

## 종합 결론

```
1순위   google.gemma-3-27b-it   전 축 만점, haiku 동점, 비용 1/8~1/11
대조군  claude-haiku-4.5        전 축 만점이지만 비쌈 — "비싼 모델이 더 낫지 않다"의 증거
보류    gpt-oss-120b            품질은 통과권이나 숨은 추론토큰 과금 + truncation 위험
탈락    qwen3-coder-30b-a3b     라우터(v8)·디자인유지(v10 D)·환각방지(v10 H) 세 축에서 반복 열세
```

- **체급이 답이 아니다**: 로컬 `qwen2.5:7b`(7B, 라우터 17/24)가 Bedrock
  `qwen3-coder-30b`(30B, 라우터 16/24)보다 낫다 — 계열마다 강한 축이 다르다.
- **v8~v9의 만점은 baseline이 단순해서 나온 착시였다** — v10이 실제 템플릿으로
  바꾸자 qwen만 무너졌다. **baseline을 실제 서비스 조건으로 올리기 전까지는
  변별이 안 된다**는 게 v8→v10 전체의 방법론적 교훈이다.

## 남은 확인 사항

- **되묻기(①)**: "혜택 내용 없이 추가 요청" 시 되묻는 동작은 백엔드 설계가 아직
  안 정해져 v10에서 아예 측정 대상에서 뺐다. 설계가 정해진 뒤 새 버전에서 잰다.
- **v10 결과표와 원자료(CSV) 불일치**: README §6의 최종표는 채점기를 네 번 고친
  뒤 원문을 재채점한 값인데, `result_csv/*.csv`의 `ok` 컬럼에는 그 재채점이
  반영돼 있지 않다(예: gemma 1차 attempt 27건 중 CSV상 `ok=True`는 9건뿐).
  결론 자체를 의심할 근거는 아니지만, CSV만 보고 감사하면 숫자가 안 맞는다 —
  재채점 결과를 CSV로도 갱신하거나 README에 각주를 남기는 정리가 필요하다.
- **`slot_invented` 재현성**: qwen에서 난 사례가 표본(H3 1건)뿐이라, 다른
  케이스·다른 슬롯 구성에서도 재현되는지는 추가 표본이 필요하다.
- **gpt-oss-120b 재시도 비용**: v10 1차 통과율 6/9로 재시도 의존도가 높다 —
  Bedrock에서 재시도는 과금이라 실질 비용은 1차 통과율 기준으로 봐야 한다.
