# Ollama 로컬 LLM 모델 선정 — 종합 결과 보고서 (v1~v4)

작성: 윤기 · 2026-09-17
대상: 뉴벤트 팀 — "AI 기반 이벤트 페이지 제작 및 게시 관리 시스템" 프로젝트

---

## TL;DR

- **최종 선정 후보: `qwen2.5:7b`, `qwen2.5-coder:7b`** — v1~v4 전 구간에서 가장 안정적이고, 실제 제품 템플릿 기준(v4)에서도 규격 위반 0건.
- **수정(편집) 경로는 S(HTML 블록 직접 수정)가 J/K(JSON 계획·패치)보다 낫다** — v2에서 J/K가 유리해 보였던 건 인공 문서 조건의 착시였고, v4가 실제 템플릿으로 재검증해서 뒤집었다.
- **신규 생성 경로(S-T vs J-T)는 아직 결론이 안 났다** — 실제 템플릿 기준 생성 시 출력 토큰이 캡을 초과해 미측정 상태.
- `gemma3:4b`·`llama3.2:3b`는 여러 버전에 걸쳐 반복적으로 탈락 사유가 확인됨.

---

## 1. 왜 버전이 4번 바뀌었나 (방법론 변천사)

| 버전 | 무엇을 쟀나 | 측정 조건 |
|---|---|---|
| **v1** | 기본 생성·편집·라우팅 (D·E·JS·N·S·C·R 7개 군) | 인공 문서(370~590자) |
| **v2** | JSON 계획/패치 도입 (J·K·CHAIN) — "서버가 마크업을 소유하면 더 안전하지 않을까"라는 가설 검증 | 인공 문서 |
| **v3** | JS 인터랙션 3방식 정면 비교(JS-HTML/JS-PLAN/JS-PATCH) + CHAIN 4단계 확장(생성→수정→JS추가→JS수정) + K3/K9 스키마 허점 재검증(K-CONTENT) | 인공 문서, num_predict 3072로 상향(캡 부족 실패 제거 목적) |
| **v4** | **채점기를 통일**하고 **실제 제품 템플릿**(4,351~5,356자)으로 S와 J를 같은 자로 재측정 | 실제 템플릿(template_1~5.html) |

> **핵심 원칙**: v1~v3의 "J/K가 유리하다"는 결론은 인공 문서 조건에서만 유효하다. v4가 실제 템플릿 + 통일된 채점기로 재보니 뒤집혔다. 따라서 이 문서를 인용할 때는 v2/v3 결과를 "방법론 발전 과정"으로만 쓰고, **실제 채택 근거는 v4 기준**으로 삼아야 한다.

### v4 — 실제 제품 템플릿 + 통일 채점기 (핵심 반전)

| 모델 | S-E (HTML 수정) | K-T (JSON 패치) |
|---|---|---|
| **qwen2.5:7b** | **25/25** | 15/25 |
| **qwen2.5-coder:7b** | **25/25** | 13/25 |
| exaone3.5:7.8b | 20/25 (`class_lost` 15건 재현) | 13~15/25 |
| gemma3:4b | 16~19/25 | **0~1/25 (탈락)** |

- **S(HTML) 경로가 K(JSON) 경로보다 우세** — v2에서 J/K가 유리해 보인 건 인공 문서 조건의 착시.
- 클래스 보존: qwen2.5:7b·qwen2.5-coder:7b는 위반 0건 — "J만 클래스를 안 깨뜨린다"는 전제가 무너짐.
- K는 구조 변경(추가/삭제)을 거의 못 함: 문구 교체 20/20, 구조 변경 3~7/20. 지배적 실패는 `no_ops`.
- 기기 간 재현성: qwen2.5:7b 96%, gemma3:4b 80%(최저 — 마크업 파손이 잦아 판정이 기기마다 흔들림).

## 4. 아직 남은 과제 (v4가 스스로 명시한 한계)

1. **신규 생성 비교 (S-T vs J-T)** — 실제 템플릿 생성 시 출력 토큰이 1,985~2,443인데 캡이 1536이라 측정 자체가 안 됨. v3에서 도입한 `Case.num_predict` 케이스별 오버라이드 방식으로 새 케이스 파일을 만들어야 진행 가능.
2. **5단계 누적 수정 비교 (E×5 vs K×5)** — v3 CHAIN5/6이 원래 이 역할을 할 계획이었으나 구현 단계에서 다른 것(JS 교차조합)으로 대체됨. 여전히 미착수.
3. **전역 CSS 전파** — J(JSON) 경로만 가능한 기능. 성능 문제가 아니라 "제품에 이 기능이 필요한가"를 팀이 먼저 결정해야 함.
4. 기타 v4 문서상 한계: `PLACEHOLDER` 정규식이 template_3의 실제 문구를 오탐, `backend=cpu` 라벨이 `nvidia-smi` 유무로만 판단해 AMD/내장 GPU 기기를 잘못 표시.
