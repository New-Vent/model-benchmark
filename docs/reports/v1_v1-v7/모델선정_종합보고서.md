## TL;DR

- **최종 후보: `qwen2.5:7b`, `qwen2.5-coder:7b`** — 인공 문서(v1~v3)·실제 템플릿 수정(v4)·
  실제 템플릿 생성(v5)·전체 파이프라인(v7) 전 구간에서 거의 무결점이다. **v4·v5·v7에서
  완전 동률**이라 이 저장소의 데이터만으로는 둘을 가를 수 없다.
- **수정(편집) 경로는 S(HTML 블록 직접 수정)가 J/K(JSON 계획·패치)보다 낫다** —
  v2에서 J/K가 유리해 보였던 건 인공 문서 조건의 착시였고, v4가 실제 템플릿으로 뒤집었다.
- **신규 생성 경로는 S-T·J-T 어느 쪽도 무방하다** — v4에서 미측정이었던 이 축을 v5가
  실제 템플릿 크기로 측정했고, qwen 계열은 두 방식 모두 100/100 동률이었다.
- **`exaone3.5:7.8b`는 JSON을 다루는 모든 단계에서 탈락 확정이다.** 생성(J-T 1/50)·
  수정(K-T)·맨눈 변환(v7 CHAIN7-S 0/10) 전부 "텍스트 필드에 마크업을 못 뺀다"는 같은
  결함의 변주이고 2기기에서 재현된다. S(HTML) 단독 경로로는 여전히 쓸 만하다.
- **`gemma3:4b`는 탈락 확정이다.** 생성은 84%로 나쁘지 않지만 패치(K) 계열이 v2·v4에서
  반복 전멸했고, v7 CHAIN7에서도 0/10·0/10으로 재확인됐다.
- **모델에게 "지어낼 것"을 안 주면 실패가 사라진다(v6).** 문구 생성을 빼고 구조만
  내게 하거나(`J-STRUCT`), `remove_item` 대신 `set_field itemCount`로 표현을 바꾸면
  (`K-COUNT`) 0%였던 축이 100%로 올라온다 — **모델을 바꾸는 것보다 요청 형태를
  바꾸는 쪽이 효과가 컸다.**

## 1. 왜 버전이 7번 바뀌었나 (방법론 변천사)

| 버전 | 무엇을 쟀나 | 측정 조건 |
|---|---|---|
| **v1** | 기본 생성·편집·라우팅 (D·E·JS·N·S·C·R 7개 군) | 인공 문서(370~590자) |
| **v2** | JSON 계획/패치 도입 (J·K·CHAIN) — "서버가 마크업을 소유하면 더 안전하지 않을까"라는 가설 검증 | 인공 문서 |
| **v3** | JS 인터랙션 3방식 정면 비교(JS-HTML/JS-PLAN/JS-PATCH) + CHAIN 4단계 확장(생성→수정→JS추가→JS수정) + K3/K9 스키마 허점 재검증(K-CONTENT) | 인공 문서, num_predict 3072로 상향(캡 부족 실패 제거 목적) |
| **v4** | **채점기를 통일**하고 **실제 제품 템플릿**(4,351~5,356자)으로 S와 J를 같은 자로 재측정 | 실제 템플릿(template_1~5.html) |
| **v5** | v4가 못 쟀던 **신규 생성**(S-T vs J-T)을 실제 템플릿 크기로 재측정 | 실제 템플릿, `checks_v4`를 `base/`로 승격 |
| **v6** | 요청 형태를 바꿔 실패를 없애기 (`J-STRUCT`·`J-STRUCT-V`·`K-COUNT`) | 구조만 출력(문구 없음) / `set_field itemCount` |
| **v7** | v4~v6이 확정한 조합(생성=S/J, 수정=E, 인터랙션=JS-PLAN)을 실제 스케일의 **전체 파이프라인**으로 연결 | 실제 템플릿, 4단계 CHAIN |

> **핵심 원칙**: v1~v3의 "J/K가 유리하다"는 결론은 인공 문서 조건에서만 유효하다. v4가
> 실제 템플릿 + 통일된 채점기로 재보니 뒤집혔다. 이 문서를 인용할 때는 v2/v3 결과를
> "방법론 발전 과정"으로만 쓰고, **실제 채택 근거는 v4~v7 기준**으로 삼아야 한다.

### v4 — 실제 제품 템플릿 + 통일 채점기 (핵심 반전)

| 모델 | S-E (HTML 수정) | K-T (JSON 패치) |
|---|---|---|
| **qwen2.5:7b** | **25/25** | 15/25 |
| **qwen2.5-coder:7b** | **25/25** | 13/25 |
| exaone3.5:7.8b | 20/25 (`class_lost` 15건 재현) | 13~15/25 |
| gemma3:4b | 16~19/25 | **0~1/25 (탈락)** |

- **S(HTML) 경로가 K(JSON) 경로보다 우세** — v2에서 J/K가 유리해 보인 건 인공 문서 조건의 착시.
- 클래스 보존: qwen2.5:7b·qwen2.5-coder:7b는 위반 0건 — "J만 클래스를 안 깨뜨린다"는 전제가 무너짐.
- K는 구조 변경(추가/삭제)을 거의 못 함: 문구 교체 20/20, 구조 변경 3~7/20. 지배적 실패는 `no_ops`.
- 기기 간 재현성: qwen2.5:7b 96%, gemma3:4b 80%(최저 — 마크업 파손이 잦아 판정이 기기마다 흔들림).

### v5 — 신규 생성(S-T vs J-T), v4의 남은 과제를 해결

v4가 "출력 토큰이 캡(1536)을 초과해 미측정"으로 남겨둔 신규 생성 축을 재측정했다.

| 모델 | J-T (최종) | S-T (최종) | 합계 |
|---|---|---|---|
| **qwen2.5:7b** | **50/50 (100%)** | **50/50 (100%)** | **100/100 (100%)** |
| **qwen2.5-coder:7b** | **50/50 (100%)** | **50/50 (100%)** | **100/100 (100%)** |
| gemma3:4b | 41/50 (82%) | 43/50 (86%) | 84/100 (84%) |
| exaone3.5:7.8b | **1/50 (2%)** | 47/50 (94%) | 48/100 (48%) |

- **qwen 계열은 J-T·S-T 완전 동률(100/100)** — "수정에서는 S가 낫다"는 결론이 생성에는
  그대로 적용되지 않는다. 신규 생성은 방식을 확정할 근거가 없어 **둘 다 후보로 남긴다.**
- **exaone3.5:7.8b는 J-T에서 1/50로 붕괴** — 지배적 실패는 `tag_in_field_*`(텍스트 필드에
  마크업을 못 뺀다). S-T(94%)는 멀쩡해서, "JSON을 다루는 순간 무너진다"는 패턴이 처음
  뚜렷하게 드러난 지점.
- 실패 유형 1위가 `placeholder`(32%) — 아직 케이스 설계 자체가 "모르는 값은 지어내지
  마라"는 지시를 충분히 강제하지 못했다는 뜻이고, 이 문제의식이 v6로 이어진다.

### v6 — 요청 형태를 바꿔 실패를 없애기

"모델이 실패하는 건 능력이 아니라 요청 형태(오퍼레이션 이름·문구 생성 부담) 때문일 수
있다"는 가설을 검증했다.

| 모델 | J-STRUCT (최종) | J-STRUCT-V (최종) | K-COUNT (최종) | 합계 |
|---|---|---|---|---|
| **qwen2.5:7b** | 45/45 (100%) | 25/25 (100%) | **20/20 (100%)** | **90/90 (100%)** |
| **qwen2.5-coder:7b** | 45/45 (100%) | 25/25 (100%) | **20/20 (100%)** | **90/90 (100%)** |
| gemma3:4b | 45/45 (100%) | 25/25 (100%) | 9/20 (45%) | 79/90 (88%) |
| exaone3.5:7.8b | 40/45 (89%) | 25/25 (100%) | 10/20 (50%) | 75/90 (83%) |

- **`J-STRUCT`(문구 생성을 빼고 구조만 출력)로 바꾸자 qwen 계열이 즉시 100%** — v5의
  `placeholder` 32% 문제가 "모델에게 지어낼 걸 안 주면" 사라진다는 걸 확인.
  (1차 통과 기준으로는 qwen2.5:7b 12/70(17%)까지 떨어졌었지만, 최종 통과에서는 45/45로
  회복 — 재시도 의존도가 높다는 뜻이라 이 부분은 프롬프트를 더 다듬을 여지가 있다.)
- **`K-COUNT`(`remove_item` 대신 `set_field itemCount`)로 표현을 바꾸자 qwen 계열이
  0%대에서 100%로 반전** — v1~v4에서 반복 확인된 "삭제 오퍼레이션 회피" 문제가 **모델의
  한계가 아니라 오퍼레이션 이름의 문제**였다는 결정적 증거.
- gemma3:4b·exaone3.5:7.8b는 K-COUNT에서도 절반 수준(45~50%)에 머물러, 표현을 바꿔도
  안 풀리는 계열 고유의 한계가 남아있음을 시사.

### v7 — 확정 조합을 실제 스케일로 잇기 (CHAIN 전체 파이프라인)

v4~v6이 확정한 "생성=S 또는 J · 수정=E · 인터랙션=JS-PLAN" 조합을 실제 템플릿 크기의
4단계 파이프라인(CHAIN7)으로 이었을 때도 버티는지 검증했다.

| 모델 | CHAIN7J | CHAIN7S |
|---|---|---|
| **qwen2.5:7b** | **10/10 (100%)** | 9/10 (90%) |
| **qwen2.5-coder:7b** | **10/10 (100%)** | **10/10 (100%)** |
| gemma3:4b | 0/10 (0%) | 0/10 (0%) |
| exaone3.5:7.8b | 0/10 (0%) | 0/10 (0%) |

- **qwen 계열만 파이프라인 전체가 살아남는다** — gemma·exaone은 CHAIN7J·CHAIN7S 둘 다
  전멸(0/10)해서, 단일 축 성능과 무관하게 **체인으로 이었을 때 갈리는 게 확정됐다.**
- exaone3.5:7.8b는 CHAIN7S(HTML 경로)에서도 0/10 — v5에서 "S 단독 경로로는 여전히
  쓸 만하다"고 봤던 판단을, 다단계 체인에서는 재검토해야 한다는 신호.
- 표본은 파일럿 규모(2기기·n=10) — v1급(4기기·3000행 이상)으로 검증된 적은 없다는 점은
  여전히 남은 한계.
- 실패 유형 1위가 `chain_blocked_by_previous_stage_failure`(13%) — 앞 단계 실패가
  뒷 단계를 연쇄로 막는 구조이므로, 개별 축 통과율만으로는 체인 생존율을 못 읽는다.

## 4. 아직 남은 과제

v4가 스스로 명시했던 과제 중 v5~v7이 해소한 것과, 여전히 남은 것을 구분한다.

### 해소됨

1. ~~신규 생성 비교 (S-T vs J-T)~~ → **v5가 해결**: qwen 계열 100/100 동률로 확정.
2. ~~확정 조합이 실제 파이프라인에서도 버티는가~~ → **v7이 해결**: qwen 계열만 생존,
   gemma·exaone은 CHAIN7 전멸로 확정.

### 여전히 남음

1. **5단계 누적 수정 비교 (E×5 vs K×5)** — v3 CHAIN5/6이 원래 이 역할을 할 계획이었으나
   구현 단계에서 다른 것(JS 교차조합)으로 대체됨. v7도 4단계까지만 다뤄서 여전히 미착수.
2. **전역 CSS 전파** — J(JSON) 경로만 가능한 기능. 성능 문제가 아니라 "제품에 이 기능이
   필요한가"를 팀이 먼저 결정해야 함.
3. **v6 `J-STRUCT` 1차 통과율의 낮은 재현성** — qwen2.5:7b가 1차 12/70(17%)에서 최종
   45/45(100%)까지 재시도로 끌어올린 것이라, 재시도 없는 단일 요청 안정성은 아직 약함.
4. **v7 표본 크기** — 파일럿(2기기·n=10)뿐이라 v1급 표본으로 재검증되지 않음.
5. 기타 v4 문서상 한계(유지): `PLACEHOLDER` 정규식이 template_3의 실제 문구를 오탐,
   `backend=cpu` 라벨이 `nvidia-smi` 유무로만 판단해 AMD/내장 GPU 기기를 잘못 표시.
