# 벤치마크 공통 방법론

버전이 바뀌어도 변하지 않는 것만 여기 둡니다.
**모델 목록·파라미터·케이스 수처럼 버전마다 달라지는 조건은 `versions/<버전>/README.md`에 있습니다.**

## 1. 이 실험이 정하려는 것

```
① 네 가지 출력 방식 중 무엇을 쓸 것인가
② 어떤 모델을 쓸 것인가
③ 여러 사람이 각자 기기에서 나눠 측정해도 결과를 합칠 수 있게
```

③이 설계의 절반입니다. 기기가 다르면 시간이 몇 배씩 달라지기 때문에,
무엇을 합칠 수 있고 무엇을 합칠 수 없는지를 먼저 정하고 시작합니다.

**한 줄 규칙 — 토큰은 합쳐도 되고, 초는 합치면 안 됩니다.**

## 2. 출력 방식 4가지

|  | 이름 | LLM 이 내는 것 | 서버가 하는 것 |
| --- | --- | --- | --- |
| N | 규칙 없음 | HTML 전체 (형태 지시 없음) | 정화 · 검증 |
| S | 형태 규칙 | HTML 전체 (태그 형태를 지시) | 정화 · 검증 |
| J | 조합 계획 | `{"type":"hero","title":"…"}` | 태그 조립 · 정화 · 검증 |
| K | 패치 | `{"op":"set_field","value":"…"}` | 기준 계획에 병합 · 조립 · 검증 |

어느 방식을 실제로 실행했는지는 버전마다 다릅니다.

## 3. 케이스 군의 정의

| 군 | 재는 것 |
| --- | --- |
| D | 환각 방어 — 안 준 날짜·혜택을 지어내는가 |
| E | 왕복 단위 — 전체 재생성 vs 블록 왕복 |
| JS | 인터랙션 생성 (구조 검사만, 실행하지 않음) |
| N | 형태 규칙 없음 (대조군) |
| S | 형태 규칙 있음 |
| C | 누적 수정 — 모델 산출물 위에 여러 단계 |
| R | 라우터 정확도 — 동작 + 대상 |

군의 **의미**는 공통이고, 군마다 케이스가 몇 개인지는 버전마다 다릅니다.
세부 케이스 정의(`CASES`, `CHAIN_STEPS`, `ROUTER_CASES`)와 검증 정규식은 각 버전 스크립트 안에 있습니다.

## 4. 결과 합치기 규칙

1. digest 불일치 경고
2. base_options 불일치 경고
3. 시간은 `runner`별로만 집계, 절대 시간 비교 금지 — 비율만
4. backend(cuda/metal/cpu) 별로 나눠서 표시
5. 파라미터 크기(4B/7B/8B)는 결과표에 항상 병기
6. 보정(calibration) drift < 0.85면 그 실행의 시간 지표는 폐기

**다른 버전의 CSV는 합치지 않습니다.** 프롬프트나 채점이 달라졌으면 같은 열이라도 다른 수치입니다.

## 5. 버전을 새로 파는 기준

다음 중 하나라도 바뀌면 새 버전입니다.

- 프롬프트 (SYSTEM, 케이스 문구)
- 채점 로직 (`check_html`, `check_extra`, 실패 이름)
- 파라미터 (`BASE_OPTIONS`, `NUM_PREDICT`, `SEEDS`, 반복 횟수)
- 모델 목록에서 **빼거나 교체** (추가는 새 버전 사유가 아님 — 기존 모델의 행은 그대로 유효)
- 케이스 추가/삭제

조건이 다르면 결과를 섞을 수 없으므로, 스크립트와 결과와 분석을 한 폴더에 같이 둡니다.

## 6. 스크립트에 군을 추가하는 법

각 버전 스크립트는 단일 파일이라, 새 군을 추가할 때 건드리는 지점은 정해져 있습니다.

1. `CASES` 리스트에 새 `Case(...)` 항목 추가 (군 이름은 `group` 필드로 구분 — 예: `"J"`, `"K"`)
2. 검증 로직이 기존 `check_html`/`check_extra`로 부족하면 `check_extra`에 분기 추가
3. `self_check()`에 새 군 관련 불변조건(assert) 추가 — 로직 결함을 LLM 호출 전에 잡기 위함
4. `summary()`의 군 목록 튜플에 새 군 이름 추가

**파일을 통째로 갈아엎지 않고, 이 네 지점만 늘려가는 것이 원칙입니다.**
스크립트 작성자 한 명이 수정해서 새 버전 폴더에 넣고, 나머지는 그대로 받아서 실행만 합니다.

## 7. 실행 중 지키는 것

- 반복은 **회차 우선** 루프 — 모델별로 몰아서 돌리지 않고 회차를 바깥 루프로 둡니다 (발열 편향 방지)
- 모델 전환 시 언로드
- 실행 시작과 끝에 보정 — `eval_rate`가 얼마나 떨어졌는지로 발열 판단
- 스크립트에서 손대도 되는 것은 `RUNNER` 환경변수와 `MODELS` 주석 토글(이미 돌린 모델 건너뛰기)뿐입니다
- `script_sha256`은 `MODELS`를 토글하면 같이 바뀌므로 **전원이 같은 값일 수 없습니다.**
  같은 회차에 같은 모델 집합을 돌린 사람들끼리만 대조하고,
  조건이 같은지는 `env.json`의 `base_options` · `seeds` · `num_predict`로 확인합니다

## 8. 재실행과 표본 수

`SEEDS`가 고정되어 있고 `temperature`가 낮아서, **같은 기기에서 같은 조건으로 다시 돌리면 출력이 비트 단위로 같습니다.**

실측으로 확인했습니다. 한 사람이 같은 기기에서 두 번 돌린 720 케이스에서
`hard_ok` · `fails` · `eval_count` · `out_len` · `html_len` · `router_ok` · `done_reason` 등
**내용 컬럼 26개가 전부 일치**했고, 달라진 것은 `wall_sec` · `load_ms` · `prompt_ms` · `eval_ms` ·
`prompt_rate` · `eval_rate` 여섯 개, 즉 **시간 컬럼뿐**이었습니다.

반면 기기가 다르면 출력이 달라집니다.

| 비교 | 출력 완전일치 | 통과 여부 일치 |
| --- | --- | --- |
| 같은 기기 재실행 | 100% | 100% |
| 다른 기기, 같은 backend(cuda) | 37% | 92% |
| 다른 기기, 다른 backend(metal↔cpu) | 44% | 92% |

여기서 따라오는 규칙입니다.

- **같은 기기에서 같은 버전을 다시 돌리지 않습니다.** 시간 재측정 말고는 얻을 것이 없습니다
- 여러 사람이 각자 돌린 결과를 합치는 것은 **정당합니다** — 기기가 실제 변동 원인입니다
- **행 수는 표본 수가 아닙니다.** 실질 반복은 `seed 수 × 기기 수`입니다.
  3000행이 넘어도 케이스 하나당 반복은 seed 5 × 기기 4 = 20회입니다
- 반복을 늘리려면 `SEEDS`를 늘리거나 기기를 늘립니다. 같은 조건 재실행은 늘리는 게 아닙니다
- `temperature`를 올리는 버전에서는 결정론이 깨지므로, 그때는 같은 기기 반복에도 의미가 생깁니다

## 9. 차이가 유의한지 보는 법

케이스·seed가 고정이라 모델 A와 B는 **같은 문제를 푼 짝지은 표본**입니다.
따라서 통과율을 따로 놓고 비교하지 말고 **짝지은 검정(McNemar)**을 씁니다 —
`(runner, group, prompt_id, repeat_no)`로 짝을 맞춘 뒤, 한쪽만 통과한 케이스가
어느 쪽으로 몇 개 쏠렸는지를 봅니다.

통과율 차이 몇 %p는 대부분 노이즈입니다. 실제로 이 실험에서 통과율 2.3%p 차이는 p=0.28로
구분되지 않았고, 같은 두 모델의 **실패 유형** 차이(환각 · 비대상 무단 변경)는 p<0.05로 갈렸습니다.
**모델 선택은 통과율보다 실패의 성격으로 가르는 것이 맞습니다.**
