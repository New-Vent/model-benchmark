# LLM 이벤트 페이지 생성 — 벤치마크 계획 (v8, 원문)

> 이 문서는 팀이 확정한 벤치마크 방법론 원문입니다. `scripts/benchmark_v8.py`가 이 문서의 §2(출력 방식)·§5(케이스 그룹)·§9(실행 절차)·§11(루프 순서)를 전부 구현한 완성본입니다. **이 스크립트는 고치지 않습니다** — 코드와 이 문서가 어긋나면 이 문서가 기준이지만, 수정은 팀 합의 후 스크립트 작성자가 진행합니다.

## 1. 이 실험이 정하려는 것

```
① 네 가지 출력 방식 중 무엇을 쓸 것인가
② 어떤 모델을 쓸 것인가
③ 여러 사람이 각자 기기에서 나눠 측정해도 결과를 합칠 수 있게
```

③이 설계의 절반입니다. 기기가 다르면 시간이 몇 배씩 달라지기 때문에, 무엇을 합칠 수 있고 무엇을 합칠 수 없는지를 먼저 정하고 시작합니다.

**한 줄 규칙 — 토큰은 합쳐도 되고, 초는 합치면 안 됩니다.**

## 2. 네 가지 출력 방식

|  | 이름 | LLM 이 내는 것 | 서버가 하는 것 |
| --- | --- | --- | --- |
| N | 규칙 없음 | HTML 전체 (형태 지시 없음) | 정화 · 검증 |
| S | 형태 규칙 | HTML 전체 (태그 형태를 지시) | 정화 · 검증 |
| J | 조합 계획 | `{"type":"hero","title":"…"}` | 태그 조립 · 정화 · 검증 |
| K | 패치 | `{"op":"set_field","value":"…"}` | 기준 계획에 병합 · 조립 · 검증 |

**이번 라운드는 J·K를 "추가확장"으로 보류하고 D·E·JS·N·S·C·R만 실행한다.**

## 3. 모델 (digest 전원 확인 완료)

| 모델 | digest | 크기 | 담당 |
| --- | --- | --- | --- |
| exaone3.5:7.8b | `c7c4e3d1ca22` | 4.8 GB | 전원 공통 (보정 기준) |
| qwen2.5:7b | `845dbda0ea48` | 4.7 GB | 지원 |
| gemma3:4b | `a2af6cc3eb7f` | 3.3 GB | 주호 |
| qwen3:8b | `500a1f067a9f` | 5.2 GB | 윤기 |

qwen3:8b는 추론 모델이라 별도 축(`done_reason=="length"` 잘림 비율 확인).

## 4. 고정 파라미터

```python
BASE_OPTIONS = {
    "temperature": 0.2, "top_p": 0.9, "top_k": 40,
    "repeat_penalty": 1.1, "num_ctx": 8192,
}
NUM_PREDICT = {"html": 1536, "plan": 512, "patch": 256}
KEEP_ALIVE = "30m"
SEEDS = [42, 43, 44, 45, 46]
```

반복 5회, 회차 우선 루프(§11), 모델 전환 시 언로드, 시작/종료 보정(drift < 0.85면 시간 지표 폐기).

## 5. 케이스 그룹

| 군 | 재는 것 | 케이스 |
| --- | --- | --- |
| D | 환각 방어 | 5 |
| E | 왕복 단위 3단 | 6 |
| JS | 인터랙션 생성(정적 검증만) | 3 |
| N | 형태 규칙 없음 (대조) | 2 |
| S | 형태 규칙 있음 | 4 |
| C | 누적 수정 — 실제 산출물 | 2묶음 × 5단계 |
| R | 라우터 정확도 | 20 요청 |

세부 케이스 정의(`CASES`, `CHAIN_STEPS`, `ROUTER_CASES`)와 검증 정규식은 `scripts/benchmark_v8.py`에 전부 구현되어 있음. 다음 라운드에 군을 추가할 때는 이 파일 안의 `CASES` 리스트와 `run_one`/`run_chain`/`run_router` 패턴을 따라 추가한다 (아래 "다음 라운드에 군 추가하기" 참고).

## 6. 결과 합치기 규칙 (§11)

1. digest 불일치 경고
2. base_options 불일치 경고
3. 시간은 `runner`별로만 집계, 절대 시간 비교 금지 — 비율만
4. backend(cuda/metal/cpu) 별로 나눠서 표시
5. 파라미터 크기(4B/7B/8B)는 결과표에 항상 병기

## 6-1. 다음 라운드에 군 추가하기 (예: J·K군)

`scripts/benchmark_v8.py`는 단일 파일이라, 새 군을 추가할 때 건드리는 지점은 정해져 있습니다.

1. `CASES` 리스트에 새 `Case(...)` 항목 추가 (군 이름은 `group` 필드로 구분됨 — 예: `"J"`, `"K"`)
2. 검증 로직이 기존 `check_html`/`check_extra`로 부족하면 `check_extra`에 분기 추가
3. `self_check()`에 새 군 관련 불변조건(assert) 추가 — 로직 결함을 LLM 호출 전에 잡기 위함
4. `summary()`의 군 목록 튜플 `("D", "E", "JS", "N", "S", "C", "R")`에 새 군 이름 추가

**파일을 통째로 갈아엎지 않고, 이 네 지점만 늘려가는 것이 원칙입니다.** 스크립트 작성자 한 명이 수정하고, 나머지는 그대로 받아서 실행만 합니다(§13).

## 7. 후속 실험 (Phase 2) — 파라미터 미니 스윕

Phase 1에서 모델·출력방식이 확정된 뒤에만 진행한다. 전체를 다시 스윕하지 않고, 이미 위험 신호가 있는 파라미터 2개만 좁게 검증한다.

| 파라미터 | 검증값 | 가설 | 관찰 대상 |
| --- | --- | --- | --- |
| `repeat_penalty` | 1.0 / 1.1 / 1.3 | 높을수록 `<li>` 반복이 억제되어 `few_benefits` 증가 | S군(혜택 3개 이상 케이스)의 실패율 |
| `temperature` | 0.1 / 0.2 / 0.4 | 높을수록 문장 품질↑, 환각(D군)도 같이↑ | D군 실패율 + 블라인드 문장 품질 점수 |

`num_predict`, `top_p`/`top_k`는 스윕하지 않는다 — 전자는 `done_reason` 로그로 상한 도달 여부만 확인, 후자는 부차 효과로 판단해 고정값 유지.
