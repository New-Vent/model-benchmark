# v1

D · E · JS · N · S · C · R 군 실행. 출력 방식은 N·S만 쓰고 J(조합 계획)·K(패치)는 보류.

**이 버전에서 모델을 결정했습니다. → [결론](#결론)**

## 스크립트가 갖고 있는 내구성 장치

실행 중간에 죽으면 몇 시간이 날아가므로, 두 지점에서 예외를 삼키고 계속 갑니다.

| 장치 | 무엇을 막나 |
| --- | --- |
| `safe_soup()` | 모델이 깨진 HTML(잘못된 주석 등)을 내면 BeautifulSoup가 파싱을 거부(`ParserRejectedMarkup`)하며 실행 전체가 죽던 문제. 파싱 실패를 잡아 "빈 문서"로 취급 → `no_section` 등 실패 케이스로 정상 기록되고 실행은 계속됨 |
| `_write_with_retry()` | Windows에서 백신·인덱서가 결과 파일을 잠가 `os.replace`가 `PermissionError`로 죽던 문제. backoff로 재시도하고, 계속 잠겨 있으면 그 저장만 건너뛰고 진행 (메모리의 rows는 유지되어 다음 저장에 반영) |

> 실행 중에는 `results_v1_*.csv`를 엑셀 등으로 열어두지 마세요.

**모델 추가는 새 버전 사유가 아닙니다.** 프롬프트·채점·파라미터·케이스가 그대로면 기존 모델의
행은 유효하고, 새 CSV를 이 폴더에 넣으면 `summarize.py`가 6개 모델 표로 뽑습니다.
출력이 결정론적이라(→ [methodology §9](../../docs/common/methodology.md)) 다른 세션에서 돌려도
품질 지표는 안전하게 합쳐집니다. 시간 지표만 그 실행의 drift로 따로 판정하면 됩니다.

모델을 **빼거나 교체**하거나, 프롬프트·채점·파라미터를 바꾸면 그때는 새 버전입니다.

```python
BASE_OPTIONS = {"temperature": 0.2, "top_p": 0.9, "top_k": 40,
                "repeat_penalty": 1.1, "num_ctx": 8192}
NUM_PREDICT  = {"html": 1536, "plan": 512, "patch": 256}
KEEP_ALIVE   = "30m"
SEEDS        = [42, 43, 44, 45, 46]        # 반복 5회
```

케이스 18개 × 5회 + 체인 6단계 + 라우터 20개 × 3회. 4개 CSV 전체 digest 일치 확인.

## 실행

```bash
export RUNNER="<본인이름>"          # Windows: set RUNNER=<본인이름>
# Ollama가 localhost가 아니면(원격 서버 사용자만) 셸에 맞게 하나만:
# export OLLAMA_HOST="http://<주소>:11434"        # bash
# $env:OLLAMA_HOST = "http://<주소>:11434"         # PowerShell — set은 안 먹는다
# set OLLAMA_HOST=http://<주소>:11434              # cmd.exe
python base/run.py v1              # 이 폴더의 케이스 전부 (D·E·JS·N·S·C·R)
python base/run.py v1 D            # D군만
python base/run.py v1 N S          # 여러 군 지정 (N/S 로도 됨)
```

결과는 어느 쪽으로 돌리든 이 폴더 안으로 들어갑니다.

```
versions/v1/result_csv/results_v1_<RUNNER>_<타임스탬프>.csv
versions/v1/result_json/env_v1_<RUNNER>_<타임스탬프>.json
versions/v1/raw_v1/                시도별 원문 (git 제외)
```

검증만 (LLM 호출 없이):

```bash
python base/run.py v1 --self-check
```

> `benchmark_v1.py`는 **아래 결과표를 만들어낸 원본 단일 스크립트**입니다.
> 지금은 `base/` + `cases_*.py`로 쪼개져 있고, 이 파일은 그때 조건을 그대로
> 보존하기 위해 기록용으로만 남겨둡니다 — 새로 돌릴 때는 쓰지 마세요.

이미 돌린 모델은 `MODELS`에서 주석 처리하고 새로 추가한 것만 켜서 돌립니다.
`MODELS` 외에는 아무것도 고치지 않습니다.

> **`script_sha256`은 `MODELS` 주석을 토글하면 같이 바뀝니다.** 그래서 전원이 같은 값일 수 없습니다.
> 이 해시는 "**같은 회차에 같은 모델 집합을 돌린 사람들끼리**" 대조하는 용도로만 쓰세요.
> 프롬프트·채점·파라미터가 같은지는 `env_v1_*.json`의 `base_options`·`seeds`·`num_predict`로 확인하는 편이 확실합니다.

총 3362행. `base_options` · `seeds` · `num_predict` · `keep_alive` · `max_retry`는 네 명 전부 일치합니다.
drift가 셋 다 1.0을 넘는 것은 **끝에서 오히려 빨라졌다**는 뜻이라 발열로 인한 시간 왜곡은 없습니다.

### 주의 1 — 주호의 시간 지표는 검증할 수 없습니다

주호는 `calibration_end`가 없어 drift가 계산되지 않았습니다. qwen3:8b에서 중단하면서 종료 보정까지
가지 못한 것으로 보입니다. 합치기 규칙 §4.6(`drift < 0.85`면 시간 지표 폐기)을 적용할 근거가 없으므로,
**주호 열의 응답시간은 발열 여부가 확인되지 않은 값**으로 읽어야 합니다.
통과율·토큰 등 나머지 지표는 시간과 무관하므로 그대로 유효합니다.

### 주의 2 — 주호만 `script_sha256`이 다릅니다

| runner | script_sha256 |
| --- | --- |
| 윤기 | `bfc06880…` |
| 지원 | `bfc06880…` |
| 주호 | `04978454…` ← 혼자 다름 |
| 도하 | `20c4c061…` (폴더 개편 중 파일명·주석이 바뀐 시점의 값) |

윤기·지원은 같은 파일을 썼고 주호만 다릅니다. Windows에서 편집기를 거치며 줄바꿈이 CRLF로 바뀌면
내용이 같아도 해시가 달라지므로 그 가능성이 큽니다. 다만 주호의 원본 파일이 없어 확인은 불가능합니다.
`base_options`·`seeds`·케이스 수가 전부 일치하고 실패 유형 분포도 다른 runner와 같은 양상이라
실제 내용이 달랐을 가능성은 낮지만, **확인되지 않은 채로 남아 있습니다.**

# 결론

## 생성 모델: **qwen2.5:7b**

최종 통과율 80%로 1위(qwen3 제외), 호출/케이스 1.30으로 재시도가 가장 적고, gemma 대비 1.16~1.38배로 느려지는 정도입니다.

결정적인 것은 통과율이 아니라 **실패의 성격**입니다.

| 모델 | 주된 실패 | 관리자가 알아채는가 |
| --- | --- | --- |
| exaone3.5:7.8b | 비대상 블록 무단 변경 20% | **모름** — 안 건드린 줄 알았던 블록이 바뀜 |
| gemma3:4b | 환각 8.3% | **모름** — 없는 혜택·날짜가 그럴듯하게 들어감 |
| qwen2.5:7b | 요청 무시 11.1% | **즉시 앎** — 아무것도 안 바뀌니 다시 요청 |

요청 무시는 **시끄러운 실패**라 재요청으로 끝납니다. 환각과 무단 변경은 **조용한 실패**라 그대로 게시됩니다.
이벤트 페이지는 날짜와 혜택이 곧 고지 내용이므로, 조용한 실패가 더 비쌉니다.

exaone은 D군 100/100으로 환각이 0%인데도 **무단 변경 20%**가 블록 왕복 편집 설계와 정면으로 충돌해서 탈락입니다.

## 탈락: qwen3:8b

최종 81%로 수치는 1위지만 쓸 수 없습니다.

- **출력 잘림 14%, 그리고 잘린 93건이 예외 없이 전부 실패** — 추론 토큰이 `num_predict: 1536`을 먹고 HTML이 중간에 끊깁니다
- 출력 토큰 중앙값 458 tok (다른 모델 70~201 tok)
- gemma 대비 **3.3~6.8배** 느림. 도하 기준 평균 21.9초

`num_predict`를 올리면 잘림은 줄겠지만 이미 제일 느린 모델이 더 느려집니다.
**다음 버전부터 테스트에서 제외합니다.**

## 저사양 대안: gemma3:4b

3.3GB로 제일 작고 제일 빠르며, 통과율 76%로 qwen2.5와 4%p 차이입니다.
**E군(블록 왕복) 80/80 만점**으로 이 부분은 오히려 1위입니다.

다만 환각 8.3%와 D군 82/100(최하)이 걸립니다. CPU 전용 기기나 메모리가 빠듯한 환경에서만 쓰고,
쓴다면 날짜·혜택은 LLM이 쓴 값을 그대로 믿지 말고 서버가 입력값과 대조해야 합니다.

## 라우터는 별도 설계

라우터 최고 성적이 qwen2.5:7b의 **144/240 (60%)**입니다. 이 숫자로는 라우팅을 맡길 수 없습니다.

동작별로 보면 갈립니다.

- **잘함** — GENERATE·DELETE는 세 모델 모두 24/24. qwen2.5는 REWRITE_ALL·ADD도 만점
- **못함** — STYLE 12/24, MOVE 12/24, EDIT 12/48. 동작은 맞히는데 **대상 블록을 틀립니다**
- **전멸** — ASK는 exaone·qwen2.5·gemma 전부 **0/36**

따라서 설계는 이렇게 갑니다.

1. **대상 블록은 LLM에 묻지 않고 클릭으로 받습니다.** STYLE·MOVE·EDIT 실패는 전부 대상 오류입니다
