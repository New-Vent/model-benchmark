# v2

J(조합 계획) · K(패치) · CHAIN(생성→그 결과를 실제로 패치) 군.
v1에서 보류했던 **출력 방식 J·K**를 실제로 재는 버전입니다.

공통 원칙은 [docs/methodology.md](../../docs/methodology.md), 공통 코드는 [`base/`](../../base/)에 있습니다.

## v1에서 무엇이 달라졌나

| | v1 | v2 |
| --- | --- | --- |
| 군 | D · E · JS · N · S · C · R | **J · K · CHAIN** |
| LLM이 내는 것 | HTML 본문 (N·S) | **JSON** — 조합 계획(J) / 패치 오퍼레이션(K) |
| HTML을 만드는 주체 | LLM | **서버** (`registry.render_plan` — 태그는 전부 우리 것) |
| 출력 강제 | 프롬프트의 형태 규칙 | **JSON Schema** (`build_plan_json_schema` / `build_patch_json_schema`) |

v1과 **케이스·채점이 다르므로 결과 CSV를 섞지 않습니다.** J1↔S1처럼 `pair`로 묶인
케이스만, 같은 요청 문구를 쓴다는 전제 아래 수동으로 비교합니다.

> ⚠ J군의 요청 문구(P1/P2/P8/P9)는 v1 `cases_ns.py`와 **글자 그대로 같아야** pair 비교가
> 성립합니다. 두 파일이 서로 다른 버전 폴더에 있어 import로 묶여 있지 않으니,
> 프롬프트를 고칠 때는 반드시 `versions/v1/cases_ns.py`와 `versions/v2/cases_j.py`를
> 둘 다 확인하세요.

## 이 버전의 조건

파라미터·시드·모델은 v1과 동일합니다 (`base/engine.py`, 개인이 수정 금지).

```python
BASE_OPTIONS = {"temperature": 0.2, "top_p": 0.9, "top_k": 40,
                "repeat_penalty": 1.1, "num_ctx": 8192}
NUM_PREDICT  = {"html": 1536, "plan": 512, "patch": 256, "router": 128}
KEEP_ALIVE   = "30m"
SEEDS        = [42, 43, 44, 45, 46]        # 반복 5회
```

| 군 | 케이스 | 무엇을 재나 |
| --- | --- | --- |
| J | 4개 (J1 · J2 · J8 · J9) | 신규 생성을 **조합 계획 JSON**으로 냈을 때의 성공률. v1 S1·S2·S8·S9와 같은 요청 문구 |
| K | 10개 (K1~K10) | 고정 baseline 위의 **패치**. 짧은 문서(K1~K6, 약 370자) 대 긴 문서(K7~K10, 약 590자) |
| CHAIN | 1개 (CHAIN1) | J가 **실제로 만들어낸** 계획을 K가 이어받아 패치. 생성이 실패하면 `chain_blocked_by_generation_failure`로 기록하고 2단계는 돌리지 않음 |

케이스 15개 × 5회.

| 모델 | digest | 실행한 기기 |
| --- | --- | --- |
| exaone3.5:7.8b | `c7c4e3d1ca22fe92` | 윤기(cuda) · 주호(cpu 표시, 아래 참고) — 2기기 |
| qwen2.5:7b | `845dbda0ea48ed74` | 도하(metal) · 주호(cpu 표시) — 2기기 |
| gemma3:4b | `a2af6cc3eb7fa8be` | 도하(metal) · 윤기(cuda) · 주호(cpu 표시) — 3기기 |
| qwen2.5-coder:7b | `dae161e27b0e90dd` | 도하(metal) — 1기기 |

digest는 모델별로 여러 기기에 걸쳐 정확히 일치합니다 — 다른 기기끼리 비교해도 됩니다.
drift도 세 runner 전부 0.99~1.01로 정상 범위입니다.

### ⚠ `NUM_PREDICT["plan"]=512` · `["patch"]=256`가 J·K에 구조적으로 불리함

S/N군(HTML 직접생성)은 `NUM_PREDICT["html"]=1536`을 받는데, J는 512, K는 256만 받습니다.
JSON은 필드명·따옴표·`"type"/"variant"` 같은 스키마 식별자를 매번 다시 써야 해서 **같은
분량의 내용이라도 HTML보다 원래 토큰이 더 필요한 포맷**인데, 예산은 오히려 1/3~1/6밖에
안 됩니다.

실측(윤기·도하·주호 3개 기기, 4개 모델 전부)으로 `truncated` 표시가 붙은 행을 전수
확인한 결과, **17건 전부 `eval_count`가 그 모드의 캡과 정확히 일치**했습니다 — J9(exaone
5건), K3(gemma3:4b 5건·qwen2.5:7b 3건·exaone 1건), J2(qwen2.5:7b 2건)·J8(qwen2.5:7b 1건).
즉 지금까지
나온 `bad_json|truncated` 실패는 전부 모델 실력이 아니라 **순수하게 토큰 예산 부족**이었고,
이 패턴은 기기·모델을 가리지 않고 재현됩니다. 가장 내용이 많은 케이스(P9=서술형 다중 지시,
K3=블록 통째로 추가)에서만 정확히 걸린다는 점도 이 해석과 일치합니다.

반면 `missing_reason`(action:"unsupported"로 즉시 거부, eval_count 6~10)이나
`unknown_block_key`(eval_count 53~146, 캡에 한참 못 미침), `placeholder`·`lost_cta`
(eval_count 캡의 절반 이하)는 캡과 무관하게 발생해서 — 이건 예산이 아니라 진짜 모델
능력 차이로 봐도 됩니다.

`NUM_PREDICT`는 `base/engine.py`의 "팀 합의 없이 개인이 수정 금지" 상수라 여기서 임의로
올리지 않았습니다. `docs/methodology.md` §6 규칙상 파라미터 변경은 새 버전 사유이기도
합니다 — **v3에서 `plan`/`patch` 캡 상향(예: 512→900, 256→400)을 논의할 것을 제안합니다.**

## 실행

```bash
export RUNNER="<본인이름>"          # Windows: set RUNNER=<본인이름>
# Ollama가 localhost가 아니면(원격 서버 사용자만) 셸에 맞게 하나만:
# export OLLAMA_HOST="http://<주소>:11434"        # bash
# $env:OLLAMA_HOST = "http://<주소>:11434"         # PowerShell — set은 안 먹는다
# set OLLAMA_HOST=http://<주소>:11434              # cmd.exe
python base/run.py v2              # 이 폴더의 케이스 전부 (J·K·CHAIN)
python base/run.py v2 K            # K군만
python base/run.py v2 J CHAIN      # 여러 군 지정
```

결과는 어느 쪽으로 돌리든 이 폴더 안으로 들어갑니다.

```
versions/v2/result_csv/results_v2_<RUNNER>_<타임스탬프>.csv
versions/v2/result_json/env_v2_<RUNNER>_<타임스탬프>.json
versions/v2/raw_v2/                시도별 원문 (git 제외)
```

`raw_v2/`에는 원본 JSON(`*.txt`)과 함께 **서버가 렌더링한 실제 HTML**
(`*.rendered.html`)이 같이 저장됩니다 — J·K 결과는 이 파일을 브라우저로 열어 확인하세요.

검증만 (LLM 호출 없이):

```bash
python base/run.py v2 --self-check
```

비교표:

```bash
python tools/summarize.py versions/v2
```

## 결과

**3대 실행 (도하=metal, 윤기=cuda, 주호=cpu 표시), 1075행.** 모델당 기기 수는 고르지
않습니다 — gemma3:4b 3기기, exaone3.5:7.8b·qwen2.5:7b 2기기, qwen2.5-coder:7b는
아직 1기기(도하)뿐입니다. 자세한 매핑은 위 "이 버전의 조건"의 모델 표를 보세요.

### 모델 × 군 — 최종 통과 (재시도 포함)

| 모델 | J | K | CHAIN | 합계 |
| --- | --- | --- | --- | --- |
| exaone3.5:7.8b | 30/40 | 99/100 | 18/20 | **147/160 (92%)** |
| qwen2.5-coder:7b | 20/20 | 40/50 | 10/10 | **70/80 (88%)** |
| qwen2.5:7b | 40/40 | 80/100 | 20/20 | **140/160 (88%)** |
| gemma3:4b | 56/60 | **0/150** | 15/30 | **71/240 (30%)** |

### gemma3:4b — K군(패치) 전멸, 3개 기기에서 재현

`gemma3:4b`는 **K1~K10 전부, 5회차 × 3기기(도하·윤기·주호) 통틀어 단 한 번도 패치
오퍼레이션을 못 냈습니다.** 실패는 두 가지뿐입니다 — 단순 필드 수정(K1·K2·K4~K8·K10)은 `no_ops`(ops
배열 자체가 없음), 블록 추가/삭제(K3·K9)와 K7 일부는 `bad_clarify`(`action:"clarify"`를
골랐는데 `question`/`options`를 제대로 안 채움). CHAIN1의 2단계(패치)도 같은 이유로 전부
실패합니다. 반면 J(신규 생성)는 56/60으로 멀쩡합니다 — **"생성은 되는데 패치 형식 자체를
전혀 못 따라간다"**는 게 이 모델의 정체입니다. K 통과율이 0%라 위 합계표의 30%는 J만
보면 가려지는 착시라, 평균으로 이 모델을 판단하면 안 됩니다.

### 케이스별로 몰려 있는 실패 — 나머지 세 모델

| 케이스 (요청) | exaone3.5:7.8b | qwen2.5:7b | qwen2.5-coder:7b |
| --- | --- | --- | --- |
| K3 "steps 영역을 **추가**해줘" | 9/10 | **0/10** | **0/5** |
| K9 "steps 영역을 통째로 **삭제**해줘" | 10/10 | **0/10** | **0/5** |
| J8 (긴출력, 상품권 추첨) | **4/10** | 10/10 | 5/5 |
| J9 (긴서술형) | **6/10** | 10/10 | 5/5 |

**Qwen 계열(2.5·2.5-coder 둘 다)은 블록을 새로 추가/삭제하는 구조적 패치를 실질적으로
못 합니다** — qwen2.5:7b는 `unknown_block_key`(아직 없는 블록을 `set_field`/`remove_block`
으로 잘못 지칭, K3에서 60건), qwen2.5-coder는 `missing_reason`(`action:"unsupported"`로
즉시 거부하면서 이유도 안 씀, eval_count 6~10, 총 30건)으로 실패 양상만 다를 뿐 결과는
똑같이 0/10·0/5입니다. exaone은 같은 요청을 거의 완벽히 처리합니다(9/10, 10/10).

거꾸로 exaone은 J8·J9(placeholder — 문구에 대괄호 자리표시자가 남음)에서 세 모델 중
유일하게 흔들립니다(exaone은 윤기·주호 2기기에서만 돌았습니다, 도하는 미실행). **J8은
두 기기에서 회차별 성패 패턴이 정확히 일치**합니다(회차 2·4는 항상 성공, 1·3·5는 항상
실패) — 기기 노이즈가 아니라 특정 seed에서 재현되는 진짜 모델 특성입니다. J9는 두
기기가 회차 2에서만 겹치고 나머지(1·3·4·5)는 갈려서, J9 쪽은 seed 재현성까지는 아직
단정하지 않습니다.

**즉 "생성(J) 대 구조적 수정(K)"에서 세 모델이 정반대로 갈립니다**: exaone은 K에 강하고
J8/J9 같은 긴 프롬프트에 약하고, qwen 계열(둘 다)은 J에 강하고 K의 블록 추가/삭제에
막힙니다. gemma3:4b는 K를 아예 못 합니다. "패치까지 시킬 계획이면 exaone, 생성만 시킬
계획이면 qwen"이 지금까지 데이터로 보이는 방향입니다.

## 결론

**아직 최종 결론은 아닙니다** — 모델당 1~3기기 × seed 5회(`methodology.md` §9 기준 실질
반복은 기기 수 × 5)라 v1(모델당 4기기)만큼 두텁지 않고, qwen2.5-coder는 아직 1기기뿐이라
특히 이릅니다. 짝지은 검정(§10, McNemar)도 아직 안 돌렸습니다. 다만 여러 기기에서
일관되게 재현된 패턴은 이렇습니다.

1. **gemma3:4b는 K(패치) 자체가 불가능합니다 — 0/150, 돌려본 3기기 전부.** J만 쓸 게
   아니라면 후보에서 제외해도 될 만큼 확실한 결과입니다.
2. **qwen 계열(2.5·2.5-coder)은 J에 강하고(합쳐서 60/60), K의 블록 추가/삭제(K3·K9)에서
   막힙니다** — 실패 방식은 다르지만(각각 `unknown_block_key`/`missing_reason`) 결과는
   똑같이 0/10·0/5. 나머지 단순 필드 패치(K1·K2·K4~K8·K10)는 두 모델 다 완벽합니다.
   qwen2.5:7b는 2기기(도하·주호)에서 재현됐지만, qwen2.5-coder는 아직 도하 1기기뿐이라
   기기 특성이 아닌지는 한 기기 더 돌려봐야 확실해집니다.
3. **exaone3.5:7.8b는 정반대입니다** — K는 거의 만점(99/100)인데 J8·J9(긴 프롬프트)에서
   대괄호 자리표시자를 남기는 고유 문제가 있습니다. J8은 두 기기(윤기·주호)에서 seed별
   성패 패턴까지 정확히 일치해 진짜 모델 특성으로 보이고, J9는 아직 그 정도로 재현되진
   않았습니다.
4. **J 대 S(v1) 비교는 지난 잠정치와 달리 대부분 동률로 좁혀졌습니다** — 남은 차이는
   exaone의 J8/J9뿐이라, "JSON 계획 방식 자체가 불리하다"는 가설은 기각 쪽에 가깝습니다.
   대신 NUM_PREDICT 캡(`plan`=512, `patch`=256)이 J9·K3처럼 내용이 많은 케이스에서
   `truncated` 실패를 100%(17/17) 만들어내고 있어, 이 캡을 올리면 J/K 점수가 더 오를
   여지가 있습니다.

**지금 데이터가 시사하는 실사용 방향**: "이벤트 페이지를 새로 만들기"(J) 위주라면 qwen
계열이 유력하고, "이미 만든 페이지를 블록 단위로 고치기"(K)까지 시켜야 한다면 exaone이
훨씬 안전합니다. 구조적 수정(블록 추가/삭제)까지 요구하는 서비스라면 지금 네 모델 중
그걸 안정적으로 하는 건 exaone뿐입니다.

**남은 일**: 기기 커버리지를 맞추기 — 지금은 qwen2.5-coder가 도하(metal) 1기기뿐이고,
exaone·qwen2.5:7b는 2기기, gemma3:4b만 3기기입니다(주호는 backend 오탐이라 시간 말고
품질 지표만 참고). qwen2.5-coder를 다른 기기에서도 돌려서 지금 결과가 기기 하나만의
특성이 아닌지 확인하는 게 우선입니다. 그다음 McNemar로 exaone vs qwen 계열의 K 실패
성격 차이가 유의한지 확인, NUM_PREDICT 캡을 올린 v3 실행과 비교하는 것도 남아 있습니다.
