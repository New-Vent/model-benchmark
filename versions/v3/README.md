# v3

**우선순위 1(§2 JS 3-way 비교, §3 CHAIN2~6)이 구현 완료됐습니다.** `python base/run.py
v3 --self-check`로 LLM 호출 없이 검증 가능합니다. 아직 실제 모델로 돌려서 결과를 낸
적은 없습니다 — 그건 팀이 각자 기기에서 실행해야 하는 다음 단계입니다(§6·§7, "결과/결론"
절 참고). §3-1의 "남아있는 진짜 혼합 노선 문제"·라우터형과 §4(모델 확대)·§6(다음에 할
일)은 여전히 설계만 있고 미착수입니다. (CHAIN5/6은 원래 "5단계 누적 수정"이었다가
구현 단계에서 "생성/수정×JS 축 교차 조합 + JS로 추가한 인터랙션의 재수정 검증"으로
바뀌었습니다 — §3의 "변경 이력" 참고.)

공통 원칙은 [docs/methodology.md](../../docs/methodology.md)를 그대로 따릅니다.

## 구현 메모 — base/·tools/에 생긴 변경 4가지

1. **`base/engine.py`에 `Case.num_predict` 필드 추가** (§5의 "구현 착수 시 먼저 정해야
   한다"던 결정). `None`이면 기존과 완전히 동일(전역 `NUM_PREDICT[mode]` 사용) — v1·v2
   케이스는 이 필드를 안 쓰므로 영향이 없다(`python base/run.py v1 --self-check` /
   `v2 --self-check` 둘 다 기존과 동일하게 통과 확인함). v3 케이스만 `num_predict=3072`를
   개별로 넘겨서 전역 상수를 안 건드리고 캡을 올린다.
2. **`base/edit_lib.py` 신규** — v1 `cases_e.py`의 `canonical()`/`outside_preserved()`/
   `build_block_edit_system()`을 그대로 옮겨 공용화했다(§3에서 E 단계가 있는 CHAIN3·CHAIN6이
   이 로직을 재사용하는 선행 작업). `versions/v1/cases_e.py` 자체는 그 버전의 결과를
   낸 코드를 보존하기 위해 건드리지 않았다 — 같은 로직이 두 곳에 있지만 원본은 동결,
   재사용은 `base/edit_lib.py`에서 한다.
3. **`tools/summarize.py`에 `section_chain_pipeline()` 추가** — CHAIN은 여러 단계
   (`prompt_id`)가 한 파이프라인을 이루는데, 기존 "모델 x 군" 표는 그 단계들을 서로
   독립된 케이스처럼 그냥 더한다. 예를 들어 GEN 5/5·PATCH 5/5·JSADD 5/5·JSMOD 0/5면
   "15/20(75%)"로 보이지만, `docs/methodology.md` §4("성공 판정은 체인 전체가 기준")대로면
   끝까지 이어진 체인은 실제로 0개(0%)다. 이 문제는 CHAIN1(v2)때부터 있었지만 2단계라
   덜 두드러졌고, 이번 4단계 체인들에서는 왜곡이 훨씬 커진다. 새 섹션은 각 단계 행에
   이미 붙어 있는 `pair` 필드(체인 ID)로 같은 체인의 단계를 묶어 "체인 전체가 끝까지
   성공했는가"를 따로 집계한다(CHAIN4의 "K 또는 E" 우회 설계는 `CHAIN_FALLBACK_RULES`로
   별도 처리). **CHAIN 결과는 "모델 x 군" 표의 CHAIN 열이 아니라 이 새 섹션으로 읽을 것.**

## 2. JS군 — HTML 방식 vs JSON 방식을 정면으로 붙인다

지금까지 "LLM이 인터랙션을 어떻게 만드는가"를 실제로 재본 적이 없습니다. 세 가지 요청
(카운트다운·아코디언·확인메시지)을 **세 가지 처리 방식**으로 각각 재현해서 정면 비교합니다.

| 방식 | LLM이 내는 것 | 실행 방식 | 위험 |
| --- | --- | --- | --- |
| **JS-HTML** | `<script>` 코드 자체 | v1의 스텁(JS1~JS3)을 그대로 채움 | LLM이 문법이 깨진 JS를 낼 수 있음 — 원래 이걸 확인하려고 만든 대조군 |
| **JS-PLAN** | countdown/faq/tabs 블록의 콘텐츠 값(JSON) | J군에 신규 케이스 추가, `add_block`이 아니라 신규 생성에 이 블록 포함 요청 | 서버가 고정 JS(`COUNTDOWN_SCRIPT`/`TAB_SWITCHER_SCRIPT`)를 붙이므로 JS 자체는 절대 안 깨짐 — 대신 날짜 형식·질문/답변 파싱 같은 "값" 오류만 남음 |
| **JS-PATCH** | 위와 동일한 콘텐츠 값(JSON), 단 `add_block` 오퍼레이션으로 | K군에 신규 케이스 추가(v7 스크립트의 K14~K16과 같은 발상) | JS-PLAN과 위험은 같고, 이미 있는 페이지에 "나중에 추가"하는 실전 시나리오까지 재현 |

**읽는 법**: JS-HTML의 실패율이 JS-PLAN/JS-PATCH보다 확연히 높게 나오면, "인터랙션은
LLM이 직접 코드로 짜게 하면 안 되고, 서버가 이미 검증한 컴포넌트에 값만 채우게 해야
한다"는 지금 설계 방향(§0, `registry.py` 주석)이 데이터로도 확정됩니다. 반대로 셋이
비슷하면 재고할 근거가 됩니다.

**구현 완료** — `versions/v3/cases_js_html.py`(JSHTML1~3, v1 JS1~JS3 완성본 이식),
`versions/v3/cases_js_plan.py`(JSPLAN1~3 — 카운트다운/FAQ/탭을 J로 요청),
`versions/v3/cases_js_patch.py`(KPATCH1~3 — 동일 요청을 `add_block`으로).

⚠ **구현 중 발견한 기존 한계**: `registry.build_patch_json_schema()`의 `add_block`
분기는 `op`/`type`/`variant`만 허용한다(`additionalProperties:false`) — 새로 추가하는
블록에 `title`/`items`/`target_date` 같은 콘텐츠 필드를 실을 방법이 스키마상 없다.
v1·v2의 K3/K9(steps 블록 `add_block`)가 지금까지 "성공"으로 보였던 건, `keep` 목록에
`steps`가 없어서(`REQUIRED`에 steps가 없음) 블록이 내용 없이 비어 렌더링돼도 `lost_steps`로
안 잡혔기 때문이다 — 실제로 내용이 채워졌는지는 지금까지 한 번도 확인되지 않았다.
JS-PATCH는 "블록이 실제로 동작 콘텐츠와 함께 렌더지는가"가 핵심이라 이 문제를 피해갈 수
없었고, `cases_js_patch.py`에 `add_block`에 한해 콘텐츠 필드까지 포함하는 확장 스키마를
새로 만들어 썼다(`registry.build_patch_json_schema()` 자체는 v1·v2가 그대로 쓰므로 건드리지
않음). **K3/K9류 케이스의 이 gap 자체를 고치는 건 이번 v3 범위 밖이다** — §6에 다음 할 일로
남긴다.

## 3. CHAIN 확장 — 생성 × 수정 × JS 축을 4가지 조합으로 전부 이어 붙인다

지금 CHAIN1은 "J로 생성 → 그 결과를 K로 패치" 하나뿐입니다. 실제 서비스 흐름은
**생성 → 수정 → JS 추가 → (그 JS를) 다시 수정**까지 이어지고, 각 축마다 "HTML 직접"
방식과 "JSON 안전" 방식 중 고를 수 있습니다. v2에서 이미 확인한 대로 **모델마다 강한
축이 다릅니다** — exaone은 수정(K)엔 강하고 긴 문서 전체재작성엔 약함, qwen 계열은
생성(J)엔 강하고 K의 구조적 오퍼레이션(`add_block`/`remove_block`)엔 약함.

> **변경 이력**: 이 절은 원래 "수정을 5단계 누적하는 C군(묶음A=E×5, 묶음B=K×5)"을
> CHAIN5/6으로 넣을 계획이었으나, 실제 구현 단계에서 우선순위를 재조정해 **뺐다**. 대신
> "생성/수정 축과 JS 축을 섞은 교차 조합"(아래 표의 CHAIN5/6)과 "JS로 추가한 인터랙션이
> 나중에 다시 수정도 되는가"(아래 4단계)를 채웠다 — 인터랙션을 "추가"만 해보고 안
> 끝내는 게 실사용에 더 가깝다는 판단.

세 축을 한 표로 정리하면:

| 축 | HTML 표현 | JSON 표현 |
| --- | --- | --- |
| 생성 | S | J |
| 수정 | E | K |
| JS 추가 | JS-HTML | JS-PATCH(`add_block`) |
| JS 수정(추가된 인터랙션 값 변경, 예: 날짜) | 전체 재작성(HTML) | K의 `set_field`(JSON) |

### 구현된 CHAIN (생성×수정×JS×JS수정 4단계, 축 조합을 그대로 케이스로)

| CHAIN | 생성 | 수정 | JS 추가 | JS 수정 | 무엇을 재나 | 상태 |
| --- | --- | --- | --- | --- | --- | --- |
| **CHAIN1** | J | K | — | — | 이미 확인됨(v2 README) — 순수 JSON 노선의 앞 2단계 | 완료(v2) |
| **CHAIN2** | J | K | JS-PATCH | K(`set_field`) | **순수 JSON 노선** 4단계 완주 — 추가뿐 아니라 나중에 그 값(날짜)까지 고쳐지는지 | **구현 완료** |
| **CHAIN3** | S | E | JS-HTML | 전체 재작성 | **순수 HTML 노선** — CHAIN2의 정반대 극단과 정면 비교 | **구현 완료** |
| **CHAIN4** | J | K 시도 → 실패 시 E로 재시도 | — | — | "K가 못 하면 E로 우회"가 qwen 계열의 K3/K9을 구제하는지 | **구현 완료** |
| **CHAIN5** | J | K | **JS-HTML** | 전체 재작성 | **교차 조합 1** — JSON으로 생성·수정한 페이지에 인터랙션만 HTML로 직접 얹으면 어떻게 되는지 | **구현 완료** |
| **CHAIN6** | S | E | **JS-PATCH류**(§3-1 참고) | K(`set_field`, 미니 계획) | **교차 조합 2** — HTML로 생성·수정한 페이지에 인터랙션만 JSON 방식으로 안전하게 얹으면 어떻게 되는지 | **구현 완료** |

CHAIN2/3/5는 표현을 안 바꾸므로 구현이 직접적입니다. CHAIN4도 역변환이 필요 없습니다 —
K의 baseline은 `render_plan()`으로 이미 HTML을 갖고 있으니, K가 실패하면 그 HTML을
그대로 E에 넘겨 재시도하면 됩니다.

**CHAIN2/3/5/6에 공통으로 붙인 4단계(JS 수정)가 이번에 새로 확인하는 것**입니다 —
"카운트다운을 추가할 수 있다"와 "추가된 카운트다운의 마감일을 나중에 고칠 수 있다"는
서로 다른 능력입니다. 실전에서는 인터랙션을 한 번 넣고 끝나는 게 아니라 날짜·문구 같은
내부 값을 계속 고치게 되므로, 추가만 검증하고 끝내면 반쪽짜리 결과입니다.

⚠ **CHAIN3/5의 4단계 검증은 CHAIN2/6보다 약합니다**: CHAIN2/6은 마지막까지 JSON을
추적하므로(`set_field` 오퍼레이션 자체를 파싱해서 값이 정확히 `2026-09-15`인지 확인)
날짜 수정 여부를 정확하게 판정합니다. 반면 CHAIN3/5는 JS-HTML(자유형식 HTML)로
끝나서 페이지를 다시 JSON으로 되돌릴 방법이 없으므로, "새 날짜 문자열이 나타나고 옛
날짜 문자열이 사라졌는가"라는 텍스트 검사(`check_date_updated`)로만 판정합니다 — 모델이
날짜 형식을 지시대로 안 쓰면(예: ISO 대신 "9월 15일") 실제로는 맞게 고쳤어도 실패로
잘못 판정될 수 있습니다. **이 비대칭 자체가 하나의 발견**입니다 — JSON 경로는 끝까지
검증 가능하고 HTML 경로는 태생적으로 헐겁다는, 이 실험 전체의 핵심 주장을 여기서도
그대로 재현합니다. CHAIN2/6과 CHAIN3/5의 4단계 통과율을 곧이곧대로 비교하지 말 것.

### 3-1. CHAIN6이 실제로 막혔던 지점 — "혼합 노선"을 완전히 피하지 않고 부분적으로 뚫었다

원래 이 절(구 우선순위 2)은 S(HTML)로 만든 페이지에 K(JSON)를 잇는 조합을 "S가 낸
HTML을 K가 이해할 JSON 계획으로 역변환해야 하는데 그런 파서가 없다"는 이유로 통째로
보류해뒀습니다. 실제로 **페이지 전체**를 JSON으로 되돌리는 범용 파서는 지금도 없고,
이번에도 만들지 않았습니다 — 그런 파서는 여전히 별도의 큰 작업입니다.

다만 CHAIN6이 필요로 하는 건 "페이지 전체를 이해하는 것"이 아니라 "새 블록 하나를
추가하는 것"뿐이라는 점에 착안해 이 특정 케이스만 풀었습니다. `add_block`은 원래
기존 콘텐츠를 몰라도 되는 오퍼레이션이라(그냥 "이거 하나 더 놓아줘"), LLM에게 페이지
전체 대신 "새로 추가할 블록 하나"만 JSON으로 받고(`_run_add_single_block_stage`),
그 블록만 `registry.render_plan`으로 렌더링해서 `edit_lib.replace_block`으로 기존
HTML에 이어붙이면 된다는 게 핵심입니다. 그렇게 추가된 블록은 그 JSON을 우리가 직접
쥐고 있으므로, 그 다음 단계(날짜 수정)는 페이지 전체가 아니라 "그 블록 하나짜리 미니
계획"에 대한 평범한 K 패치로 표현할 수 있습니다 — 미니 계획이라는 우회로가 통했을 뿐,
"임의의 HTML을 임의로 수정"하는 범용 역변환 문제는 여전히 안 풀렸습니다.

**남아있는 진짜 혼합 노선 문제** — 아래는 여전히 막혀 있고 이번에도 안 만들었습니다.

| | ① 생성 | ② 수정 | 막히는 지점 |
| --- | --- | --- | --- |
| CHAIN-혼합A | S(HTML) | K(JSON) | S가 낸 페이지의 **기존** hero/benefits/cta를 K로 고치려면(새로 추가가 아니라) 그 블록들을 JSON 계획으로 역변환해야 함 — 여전히 없음 |
| CHAIN-혼합B | J(JSON) | E(HTML) | `render_plan` 결과를 E에 넘기는 건 됨(단방향, CHAIN5가 이미 이 경로를 씀) — 문제는 E가 고친 HTML을 **다시 JSON 계획으로 되돌려야** 그 다음 단계(예: 다시 K로 패치)가 이어짐 |

### 우선순위 스트레치 — 라우터가 축 선택을 직접 하게 하기

CHAIN1~6은 "이번엔 J로, 이번엔 S로"를 **사람이 미리 정해서** 돌립니다. 더 실전에 가까운
건 자연어 요청을 연달아 던지고 **R(라우터)이 매번 "이건 생성/수정/JS 중 뭐고, 그중 어떤
축(HTML/JSON)인지"까지 직접 판단**해서 이어가는 것입니다. 지금 라우터의 정답 op는 이
"3축 중 뭔지" 판단을 다루지 않으므로 정답 체계 자체를 확장해야 합니다 — CHAIN1~6 결과를
본 뒤 v4 후보로 남깁니다.

**구현 완료** — `versions/v3/cases_chain.py`에 CHAIN2~CHAIN6 전부 있음. E 단계가 있는
CHAIN3·CHAIN6은 `build_block_edit_system`을 재사용했고(→ `base/edit_lib.py`로 먼저 옮김,
위 "구현 메모" 참고), CHAIN6의 JS 추가 단계는 위 §3-1의 "블록 하나만 JSON으로 받는" 새
메커니즘(`_run_add_single_block_stage`)으로 구현했다. `engine.run_one()`은 검증에
성공한 콘텐츠(파싱된 plan, 렌더링된 html)를 호출자에게 안 돌려주므로, 그 핵심 루프를
복제하되 성공 콘텐츠까지 반환하는 `_run_stage()`를 `cases_chain.py`에 새로 뒀다 —
CHAIN1(v2)이 생성 단계 하나에만 하던 걸 html/plan/patch 세 모드 전부로 일반화한 것.

§3-1의 "남아있는 진짜 혼합 노선 문제"와 라우터형(우선순위 스트레치)은 이번에도 안
만들었다 — 범용 HTML→JSON 역변환이 없어서 막힌다는 문제가 그대로 남아있고, v3 범위
밖으로 유지한다.

## 5. `NUM_PREDICT` 전부 3072로 통일

```python
# 지금(v1·v2, base/engine.py)
NUM_PREDICT = {"html": 1536, "plan": 512, "patch": 256, "router": 128}

# v3 제안
NUM_PREDICT = {"html": 3072, "plan": 3072, "patch": 3072, "router": 3072}
```

**근거**: v2 실측에서 `truncated` 실패 17건(→ 실제로는 9개의 고유 (모델·케이스·기기·seed)
조합) 전부가 그 모드의 캡과 **정확히 일치**했습니다 — J9(exaone)·K3(gemma3:4b·qwen2.5:7b)가
캡 부족으로 잘렸습니다. 캡을 없애면 이 실패들은 사라집니다.

**과대 기대 금지**: 같은 실측에서, 캡을 3072로 올려도 **고쳐지지 않는 것**도 이미
확인했습니다 — qwen 계열의 `unknown_block_key`/`missing_reason`(캡의 1/3도 안 쓰고
실패), gemma3:4b의 K 전멸(`bad_clarify`/`no_ops`, 역시 캡과 무관), exaone의 텍스트
필드 HTML 주입(캡에 한참 못 미치는 시도에서도 발생)은 **모델 능력 문제**라 캡을 올려도
그대로입니다. v3의 목적은 "캡 때문에 밀리는 억울한 실패를 없애서, 남은 실패가 전부
진짜 모델 문제라고 확실히 말할 수 있게 하는 것"이지, 점수를 끌어올리는 게 아닙니다.

이건 `base/engine.py`의 "팀 합의 없이 개인이 수정 금지" 상수를 바꾸는 것이라
`docs/methodology.md` §6 규칙상 그 자체로 새 버전(v3) 사유입니다 — 그래서 이 문서가
v3로 분리돼 있습니다.

**구현 완료** — 전역 `NUM_PREDICT`는 그대로 두고, `Case`에 `num_predict` 필드를 추가해
케이스 단위로만 3072를 오버라이드했다(위 "구현 메모" 1번 참고). "v1·v2는 원래 조건
그대로 재현 가능해야 한다"는 원칙과 충돌하지 않도록, `base/`는 여전히 하나뿐이고
v1·v2 케이스는 이 필드를 아예 안 쓴다.

## 6. 이번엔 안 하는 것 (다음 후보)

- **컴포넌트/variant 교체 오퍼레이션**(`replace_block` 등) — §1의 세 번째 구멍. 별도 설계
  검토가 더 필요해서 v3 범위에서 뺐습니다.
- **콘텐츠 필드 안의 HTML 태그 주입 검사** — §1의 네 번째 구멍. `check_plan`/`check_html`에
  텍스트 필드 안의 `<strong>`/`<span>` 같은 태그를 잡는 로직이 아직 없습니다.
- **K3/K9류 add_block의 "내용 없이 성공 처리"되는 gap** — §2에서 발견한 것. JS-PATCH만
  콘텐츠 필드 스키마로 우회했고, `registry.build_patch_json_schema()` 자체는 안 고쳤습니다.
- **§3-1의 "남아있는 진짜 혼합 노선 문제"**(CHAIN-혼합A/B) — 범용 HTML→JSON 역변환 파서가
  필요한 큰 작업입니다.
- **라우터가 축 선택을 직접 하게 하기**(우선순위 스트레치) — CHAIN1~6 결과를 본 뒤 v4 후보.
- **모델 확대**(§4) — 설계만 있고 미착수.

## 7. 무엇을 빼고 무엇을 남기나 (실측 기준)

v1·v2 CSV를 다시 훑어서, **6개 모델 전부에서 흔들림 없이 결론이 난 것**은 v3의 기본
매트릭스에서 빼고 회귀 확인용으로만 가끔 돌립니다. 아직 답이 안 갈렸거나 신규 모델에서
다시 봐야 하는 것만 매번 돌립니다.

## 8. 첫 실제 실행에서 나온 것 (주호, CHAIN만, 1기기 — 예비 관찰)

**아직 결론이 아닙니다** — runner 1명(주호, cpu), CHAIN 군만 407행. methodology.md §9
기준 실질 반복은 seed 5회 × 기기 1대뿐이라 v1(기기 4대)만큼 두텁지 않습니다. 다만
새 CHAIN 파이프라인 자체가 실제 모델로 정상 동작하는지, 그리고 새 집계
(`section_chain_pipeline`)가 실전에서도 의미 있는 신호를 내는지는 이걸로 확인됐습니다.

- **집계 수정이 실전에서 바로 증명됐다** — qwen2.5:7b는 "모델 x 군" 표에서 CHAIN 최종
  75/90(83%)로 보이지만, CHAIN2 파이프라인 전체 통과율은 **0/5(0%)**다. GEN·PATCH는
  각각 5/5로 완벽한데 3단계(JS 추가)에서 매번 걸려서, 단계별 합산으로는 절대 안 보이던
  "체인 자체는 한 번도 안 이어졌다"는 사실이 새 섹션으로만 드러났다.
- **qwen2.5:7b가 CHAIN2 1단계(순수 J 생성)에서 요청하지 않은 카운트다운을 스스로
  만들어 넣는 걸 발견** — 시스템 프롬프트가 "명시적으로 언급 안 된 선택 블록은
  추가하지 마라"고 명시하는데도 무시했다. 원래 GEN 단계의 `forbid=["notices"]`(v2
  cases_j.py의 관례를 그대로 따른 것)로는 이걸 못 잡아서, 실패가 조용히 3단계까지
  넘어갔다가 "카운트다운 중복"이라는 전혀 다른 증상(`duplicate_data_block_countdown`)
  으로 나타났다 — 원인(1단계)과 증상(3단계)이 갈려서 원인 파악이 오래 걸렸다.
  **수정 완료**: `cases_chain.py`의 `GEN_FORBID = ["notices","steps","countdown","faq","tabs"]`를
  만들어 CHAIN2/3/4/5/6의 GEN 단계 전부에 적용 — 이제 요청 안 한 선택 블록을 추가하면
  원인 위치(1단계)에서 바로 하드 실패로 잡힌다.
- **gemma3:4b는 v2에서 이미 문서화된 패턴을 완전히 새로운 케이스에서도 그대로 재현했다**
  — 단순 필드 패치(`CHAIN2_PATCH`)는 `no_ops`로, 구조적 블록 추가(`CHAIN4_K`의 steps
  추가)는 `bad_clarify`로 전멸. CHAIN4의 설계 의도(K 실패 시 E로 구제)도 정확히
  작동해서 K 0/5 → E 4/5로 구제됐다.
- **exaone3.5:7.8b의 CHAIN3_GEN(S 생성)이 0/5로 나온 건 v1에서 같은 모델·같은
  프롬프트(바이트 단위로 diff 확인함)가 80/80이었던 것과 크게 어긋난다.** 원인은 코드가
  아니라 실행 환경으로 보인다 — 이번 실행의 `env_v3_주호_*.json`에
  `"Warning: client version is 0.34.1"`(서버는 0.34.0)이 찍혀 있어, v1 실행 당시(경고
  없는 깨끗한 0.34.0)와 Ollama 클라이언트/서버 버전이 어긋난 상태다. 모델 digest는
  동일(`c7c4e3d1ca22fe92`)하지만, **재실행 전에 Ollama 클라이언트·서버 버전부터
  맞출 것을 권장** — 지금 상태의 exaone 데이터는 신뢰하지 말 것.
