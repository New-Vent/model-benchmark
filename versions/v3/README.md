## 2. JS군 — HTML 방식 vs JSON 방식을 정면으로 붙인다

지금까지 "LLM이 인터랙션을 어떻게 만드는가"를 실제로 재본 적이 없습니다. 세 가지 요청
(카운트다운·아코디언·확인메시지)을 **세 가지 처리 방식**으로 각각 재현해서 정면 비교합니다.

| 방식 | LLM이 내는 것 | 실행 방식 | 위험 |
| --- | --- | --- | --- |
| **JS-HTML** | `<script>` 코드 자체 | v1의 스텁(JS1~JS3)을 그대로 채움 | LLM이 문법이 깨진 JS를 낼 수 있음 — 원래 이걸 확인하려고 만든 대조군 |
| **JS-PLAN** | countdown/faq/tabs 블록의 콘텐츠 값(JSON) | J군에 신규 케이스 추가, `add_block`이 아니라 신규 생성에 이 블록 포함 요청 | 서버가 고정 JS(`COUNTDOWN_SCRIPT`/`TAB_SWITCHER_SCRIPT`)를 붙이므로 JS 자체는 절대 안 깨짐 — 대신 날짜 형식·질문/답변 파싱 같은 "값" 오류만 남음 |
| **JS-PATCH** | 위와 동일한 콘텐츠 값(JSON), 단 `add_block` 오퍼레이션으로 | K군에 신규 케이스 추가(v7 스크립트의 K14~K16과 같은 발상) | JS-PLAN과 위험은 같고, 이미 있는 페이지에 "나중에 추가"하는 실전 시나리오까지 재현 |

**읽는 법**: JS-HTML의 실패율이 JS-PLAN/JS-PATCH보다 확연히 높게 나오면, "인터랙션은
LLM이 직접 코드로 짜게 하면 안 되고, 서버가 이미 검증한 컴포넌트에 값만 채우게 해야
한다"는 지금 설계 방향(§0, `registry.py` 주석)이 데이터로도 확정됩니다. 반대로 셋이
비슷하면 재고할 근거가 됩니다.

**구현 시 만들 파일**: `versions/v3/cases_js_html.py`(v1 JS1~JS3 완성본 이식),
`versions/v3/cases_js_plan.py`(J에 카운트다운/아코디언(faq)/확인메시지 요청 3개 추가),
`versions/v3/cases_js_patch.py`(K에 동일 요청을 `add_block`으로 3개 추가, 고정 baseline
사용).

## 3. CHAIN 확장 — 생성 × 수정 × JS 축을 표 하나로 합쳐서 구현 순서까지 정한다

지금 CHAIN1은 "J로 생성 → 그 결과를 K로 패치" 하나뿐입니다. 실제 서비스 흐름은
**생성 → 수정 → JS(인터랙션 추가)** 3축으로 이어지고, 각 축마다 "HTML 직접" 방식과
"JSON 안전" 방식 중 고를 수 있습니다. v2에서 이미 확인한 대로 **모델마다 강한 축이
다릅니다** — exaone은 수정(K)엔 강하고 긴 문서 전체재작성엔 약함, qwen 계열은
생성(J)엔 강하고 K의 구조적 오퍼레이션(`add_block`/`remove_block`)엔 약함.

**"수정" 축엔 한 번만 하는 것과 5번 누적하는 것 두 켤레가 있습니다** — 이게 C군입니다:

- **묶음A** = 블록왕복(E)을 5단계 연속 적용 — `benchmark_v1.py`에 **이미 구현·실행돼
  있습니다**(C0~C5, 100%→54%로 단계마다 저하, §7 참고). base/로 이식만 하면 됩니다.
- **묶음B** = 패치(K)를 5단계 연속 적용 — **아직 한 번도 없습니다.** 신규 구현 필요.

세 축과 C묶음까지 한 표로 정리하면:

| 축 | HTML 표현 | JSON 표현 |
| --- | --- | --- |
| 생성 | S | J |
| 수정 (1회) | E | K |
| 수정 (5회 누적, C군) | 묶음A = E×5 (있음) | 묶음B = K×5 (신규) |
| JS 추가 | JS-HTML | JS-PATCH |

### 우선순위 1 — 구현할 CHAIN (축 선택을 그대로 케이스로)

| CHAIN | 생성 | 수정 | JS 추가 | 무엇을 재나 | 상태 |
| --- | --- | --- | --- | --- | --- |
| **CHAIN1** | J | K | — | 이미 확인됨(v2 README) — 순수 JSON 노선의 앞 2단계 | 완료(v2) |
| **CHAIN2** | J | K | JS-PATCH | 순수 JSON 노선 3단계 완주 — 끝까지 이어져도 안 깨지는지 | 신규 |
| **CHAIN3** | S | E | JS-HTML | **순수 HTML 노선** — CHAIN2의 정반대 극단과 정면 비교 | 신규 |
| **CHAIN4** | J | K 시도 → 실패 시 E로 재시도 | — | "K가 못 하면 E로 우회"가 qwen 계열의 K3/K9을 구제하는지 | 신규 |
| **CHAIN5** | S | 묶음A = E×5 (이식) | — | 5단계 누적 시 HTML 노선의 드리프트 곡선 재확인(이미 있는 C0~C5 데이터 재현) | 이식만 |
| **CHAIN6** | J | 묶음B = K×5 (신규) | — | 5단계 누적 시 JSON 노선의 드리프트가 묶음A(E×5)보다 덜한지 — **처음 재는 것** | 신규 |

CHAIN2/3은 표현을 안 바꾸므로 바로 구현 가능합니다(S→E는 v1 메커니즘 그대로,
J→K는 CHAIN1이 이미 증명). CHAIN4도 역변환이 필요 없습니다 — K의 baseline은
`render_plan()`으로 이미 HTML을 갖고 있으니, K가 실패하면 그 HTML을 그대로 E에 넘겨
재시도하면 됩니다(E가 고친 결과를 다시 JSON으로 되돌릴 필요는 없음, 이번 턴은 HTML로
끝남). CHAIN6이 이번 v3에서 **가장 새로운 정보**입니다 — 묶음A(E×5)는 이미 답(54%까지
저하)이 있지만 묶음B(K×5)는 완전히 미지수라, 5단계 누적에서 패치가 블록왕복보다
드리프트가 덜한지(K의 최소침습 설계가 누적에서도 이기는지)를 여기서 처음 봅니다.

### 우선순위 2 — 축을 섞는 "혼합 노선" (기술 부채 있음, 뒤로 미룸)

| | ① 생성 | ② 수정 | 막히는 지점 |
| --- | --- | --- | --- |
| CHAIN-혼합A | S(HTML) | K(JSON) | S가 낸 HTML을 K가 이해할 JSON 계획으로 **역변환**해야 함 — 이런 파서가 지금 전혀 없음 |
| CHAIN-혼합B | J(JSON) | E(HTML) | J의 계획을 렌더링한 HTML(`render_plan` 결과)을 E에 넘기는 건 됨(단방향) — 문제는 E가 고친 HTML을 **다시 JSON 계획으로 되돌려야** 그 다음 단계(예: 다시 K로 패치)가 이어짐 |

**둘 다 "HTML → JSON 역변환"이 없어서 막힙니다.** 이건 별도 파서(또는 LLM에게 "이 HTML을
보고 계획을 다시 만들어라"고 시키는 또 하나의 모드)가 필요한 큰 작업이라 v3 범위에서
빼고, 그 역변환 자체가 필요한지부터(실전에 그런 요청 흐름이 실제로 있는지) 다음 버전
논의로 넘깁니다.

### 우선순위 3 (스트레치) — 라우터가 축 선택을 직접 하게 하기

CHAIN1~6은 "이번엔 J로, 이번엔 S로"를 **사람이 미리 정해서** 돌립니다. 더 실전에 가까운
건 자연어 요청을 연달아 던지고 **R(라우터)이 매번 "이건 생성/수정/JS 중 뭐고, 그중 어떤
축(HTML/JSON)인지"까지 직접 판단**해서 이어가는 것입니다. 지금 라우터의 정답 op는 이
"3축 중 뭔지" 판단을 다루지 않으므로 정답 체계 자체를 확장해야 합니다 — CHAIN1~6 결과를
본 뒤 v4 후보로 남깁니다.

**구현 시 만들 파일**: `versions/v3/cases_chain.py`에 CHAIN2~CHAIN6 추가. CHAIN3·CHAIN4·
CHAIN5는 `versions/v1/cases_e.py`의 `build_block_edit_system`(CHAIN5는 C0~C5의 5단계
반복 로직도)을 재사용해야 하므로, 그 함수들을 `base/` 공용으로 옮기는 작업이 선행돼야
합니다(현재는 v1 폴더 안에 있어 v3에서 그대로 import할 수 없음). CHAIN6은 `cases_k.py`의
`apply_patch`를 5번 연속 호출하는 새 로직이 필요합니다. CHAIN-혼합A/B와 라우터형(우선순위
3)은 이번 v3엔 안 만듭니다.

## 5. `NUM_PREDICT` 전부 3072로 통일

```python
# 지금(v1·v2, base/engine.py)
NUM_PREDICT = {"html": 1536, "plan": 512, "patch": 256, "router": 128}

# v3 제안
NUM_PREDICT = {"html": 3072, "plan": 3072, "patch": 3072, "router": 3072}
```

**근거**: v2 실측에서 `truncated` 실패 17건(→ 실제로는 9개의 고유 (모델·케이스·기기·seed)
조합) 전부가 그 모드의 캡과 **정확히 일치**했습니다 — J9(exaone)·K3(gemma3:4b·qwen2.5:7b)가
캡 부족으로 잘렸습니다. 캡을 없애면 이 실패들은 사라집니다.

**과대 기대 금지**: 같은 실측에서, 캡을 3072로 올려도 **고쳐지지 않는 것**도 이미
확인했습니다 — qwen 계열의 `unknown_block_key`/`missing_reason`(캡의 1/3도 안 쓰고
실패), gemma3:4b의 K 전멸(`bad_clarify`/`no_ops`, 역시 캡과 무관), exaone의 텍스트
필드 HTML 주입(캡에 한참 못 미치는 시도에서도 발생)은 **모델 능력 문제**라 캡을 올려도
그대로입니다. v3의 목적은 "캡 때문에 밀리는 억울한 실패를 없애서, 남은 실패가 전부
진짜 모델 문제라고 확실히 말할 수 있게 하는 것"이지, 점수를 끌어올리는 게 아닙니다.

이건 `base/engine.py`의 "팀 합의 없이 개인이 수정 금지" 상수를 바꾸는 것이라
`docs/methodology.md` §6 규칙상 그 자체로 새 버전(v3) 사유입니다 — 그래서 이 문서가
v3로 분리돼 있습니다.

**구현 시 고칠 파일**: `base/engine.py`의 `NUM_PREDICT` (v1·v2는 그대로 두고 v3부터만
적용 — 기존 결과와 안 섞이도록 `base/`를 통째로 새로 만들지 여부는 별도 논의 필요.
지금 구조상 `base/`는 버전 공용이라, 값을 바꾸면 v1·v2를 다시 돌릴 때도 3072가 적용됨.
"v1·v2는 원래 조건 그대로 재현 가능해야 한다"는 원칙과 충돌하므로, 구현 착수 시
`NUM_PREDICT`를 버전별로 오버라이드하는 방법을 먼저 정해야 합니다 — 예: `Case`에
`num_predict_override` 필드 추가, 또는 `engine.main()`에 파라미터로 전달).

## 6. 이번엔 안 하는 것 (다음 후보)

- **컴포넌트/variant 교체 오퍼레이션**(`replace_block` 등) — §1의 세 번째 구멍. 별도 설계
  검토가 더 필요해서 v3 범위에서 뺐습니다.

## 7. 무엇을 빼고 무엇을 남기나 (실측 기준)

v1·v2 CSV를 다시 훑어서, **6개 모델 전부에서 흔들림 없이 결론이 난 것**은 v3의 기본
매트릭스에서 빼고 회귀 확인용으로만 가끔 돌립니다. 아직 답이 안 갈렸거나 신규 모델에서
다시 봐야 하는 것만 매번 돌립니다.
